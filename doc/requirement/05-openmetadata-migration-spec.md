## 1. 问题陈述

### 1.1 要解决的问题

本平台的能力集中在「**把元数据取进来**」（摄取），而「**在元数据上做判断、呈现与治理**」这一半基本是空的。`product-benchmark-roadmap.md` §1 已把这个矛盾定性为：

> 一个**表结构登记簿 + 变更告警器** → 应该是**可浏览、可治理、可审计的元数据资产平台**

本次迁移的目标不是"照抄 OpenMetadata"，而是：**从 OpenMetadata 已工程化的能力中，取出能直接补上本平台缺口的部分**，让已有数据产生业务价值出口。

### 1.2 现状事实基线（实测，决定需求范围）

| # | 事实 | 证据 |
|---|---|---|
| F1 | **Profiler 全链路为零**：`TableProfile` 模型存在但全仓无填充代码；无采样执行器、无 null/唯一/分位数/直方图实现 | `schema/data/table.py:28-40`；全 `src/` 检索 `histogram/percentile/quantile/median` 仅命中 `observability/metrics.py`（Prometheus 指标，与列级统计无关） |
| F2 | 采样 SQL 已具备，缺调用方 | `platform/dialect/*.py` 的 `sample_sql` |

### 1.3 为什么是现在

F2 + F3 意味着 Profiler 的**存储与取数两侧都已就绪，只缺中间的执行器**——这是全平台投入产出比最高的缺口，且能一次性激活 F4/F5 中的多个占位页。

## 2. 目标与非目标

### 2.1 目标（In Scope）

| 目标 | 对应需求 |
|---|---|
| G1 让平台能回答"这张表的数长什么样" | FR-M1、FR-M2 |
| G2 让用户能在不知道表名的前提下收敛到目标资产 | FR-M3 |
| G3 让血缘从"能解析"变成"敢开" | FR-M4 |
| G4 让数据质量从"跑一次"变成"可追溯" | FR-M5 |
| G5 降低自动分级误报（误判 → 脱敏 → 业务故障） | FR-M6 |
| G6 让资产详情成为治理操作入口，而非只读列表 | FR-M7 |
| G7 给本地扩展字段一个符合上游惯例的承载位 | FR-M8 |
| G8 让部分失败的任务不被误报为全量失败 | FR-M9 |

### 2.2 非目标（Out of Scope，明确不做）

| 项 | 排除理由 |
|---|---|
| Elasticsearch / 索引映射 / 搜索高亮 | 重基础设施。facet 用关系库聚合实现即可（FR-M3） |
| Airflow 编排（`openmetadata-airflow-apis`） | 本平台 `platform/orchestration` 已提供 DAG/重试/锁/取消/审计，更完整 |
| OpenMetadata Java 服务层、Kafka 事件总线 | 与 Python + PostgreSQL 技术栈不匹配 |
| `<OM-UI>/components/common/Table/TableV2.tsx`（85KB）整体搬移 | 耦合过重，仅吸收其交互模型（FR-M7.4） |
| 消息 / BI / ML / API / 文件类资产 | `product-benchmark-roadmap.md` §2.1 已判定"建议不做" |
| 存储层兼容 OpenMetadata JSON 模型 | 违反 ADR-8，会使 keyset 分页、列级索引、快照 Diff 优化全部作废 |

## 2.3 备选方案与取舍

本节回答评审者会问的第一个问题：**上游是开源的 Python 包，为什么不直接依赖它？**

### 2.3.1 被评估的方案

| 方案 | 描述 |
|---|---|
| **A** | 直接依赖：`pip install openmetadata-ingestion`，调用其 profiler / data_quality / lineage 模块 |
| **B** | 零依赖重写：只借鉴思路，全部自己实现，不复制任何代码 |
| **C（选定）** | **移植算法**：复制并改造有限代码（采样策略、分桶、分位数覆写等），不引入包依赖 |
| **D** | 折中：先用 A 快速验证，再逐步替换为自研 |

### 2.3.2 方案 A 的否决理由（实证）

| # | 论据 | 证据 |
|---|---|---|
| A-1 | **许可证是排他性的**：`ingestion/` 模块为 **Collate Community License v1.0**，非 Apache-2.0。其 §1.1 定义 Excluded Purpose——**禁止用于"提供与 Collate 产品竞争的 SaaS / PaaS / IaaS 或类似在线服务"**。本平台正是元数据治理平台，若以在线服务形态提供，存在落入排他范围的风险。这条是**否决 A 的充分条件**，无需再看其他论据 | `ingestion/LICENSE:1-45`（§1.1 Excluded Purpose）；仓库根 `LICENSE:1` 才是 Apache-2.0 |
| A-2 | **依赖体积数量级差异**：上游 `base_requirements` 为 **43 项**，本项目直接依赖 **16 项**。且这 43 项含大量与画像/质量/血缘无关的运行时依赖：`kubernetes`、`boto3`、`azure-keyvault-secrets`、`google-cloud-secret-manager`、`shapely`、`memory-profiler`、`collate-data-diff`、`dbt-extractor`、`antlr4-python3-runtime` | `ingestion/setup.py:175-225` vs `pyproject.toml:6-27` |
| A-3 | **硬钉版本易与既有环境冲突**：上游存在多处 `==` 硬钉——`chardet==4.0.0`（且 setup.py 自身注释已承认它与 `chardet>=7` 冲突）、`tabulate==0.9.0`、`antlr4-python3-runtime==4.9.2`、`cached-property==1.5.2`。任一与本项目或部署环境已有包冲突，都会演变为长期依赖地狱 | `ingestion/setup.py:176,182,211,180,96` |
| A-4 | **SQLAlchemy 版本天花板**：上游封顶 `sqlalchemy>=2.0.0,<2.1`，且其注释指出 `snowflake-sqlalchemy` 在 SA 2.1 会因重写私有 API 而崩溃。本项目声明为 `>=2.0` 无上限。引入上游即等于替本平台锁死 SA 版本 | `ingestion/setup.py:206-209`；`pyproject.toml:8` |
| A-5 | **pydantic 版本被抬升**：上游要求 `pydantic>=2.12.5,<3`，本项目为 `>=2.0`。已落地环境若低于 2.12.5 将被强制升级，波及全部现有模型 | `ingestion/setup.py:50` |
| A-6 | **实体模型语义冲突**：上游实体模型由 `datamodel-code-generator` 从 JSON Schema 生成，与其"整实体 JSON 存储"模型绑定；而 ADR-8 已判定本平台采用自有关系模型。二者不是同一数据形状，调用前必须做双向转换——**适配成本并不比移植低** | `design/03` §2；`ingestion/setup.py:482`（`datamodel-code-generator`） |
| A-7 | **上游版本为开发版**：`openmetadata-ingestion` 当前版本 `2.0.0.0.dev0`，非稳定发布版，不宜作为生产依赖 | `ingestion/pyproject.toml:9` |

**结论**：A 的许可证风险是**充分否决条件**；即使忽略许可证，A-2 ~ A-7 也使其成本高于收益。

### 2.3.3 方案 D 的否决理由

D 看似稳健，但它要求**先把 A 装进去**——一旦 `openmetadata-ingestion` 进入依赖树，A-1 的许可证风险、A-3 的版本冲突即刻生效，而"后续替换"没有强制时间点，实践中会永久拖延。**在有排他性许可证的包上做临时依赖，风险与收益不对称**，故否决。

### 2.3.4 方案 B 的否决理由

画像不是简单逻辑，其价值恰在边界情况：各库 `TABLESAMPLE` 语法差异、系统表行数估算失败后的退化、直方图 Freedman–Diaconis 在 IQR=0 时的退化与桶数封顶、分位数在无近似函数时的回退。这些是上游多年积累的**暗知识**，零依赖重写等于重踩一遍坑，且结果无法与上游对齐，为将来合入上游变更制造障碍。**不重写不等于不借鉴**：B 只适用于上游完全无参考的部分。

### 2.3.5 选定方案 C 及其代价

**C：以文件为单位移植算法与常量，改造为本平台的 `Dialect` / ORM 风格，不引入任何上游运行时依赖。**

| 代价 | 缓解 |
|---|---|
| 需长期维护移植代码 | 每个移植文件头部记录**来源文件 + 上游版本号**，纳入 `upstream_manifest.json`（既有 `design/04` §7.1） |
| 与上游逐渐分叉 | 只移植算法，不复制模块结构；建立 CI 漂移检查（见 §11 准入条件） |
| 许可证仍可能约束衍生作品 | **OQ-0 必须先行**：移植属"准备衍生作品"，法律定性需法务确认，见 §10 |

### 2.3.6 次级取舍（C 方案内部的二选一）

| 子项 | 取舍 | 决策与理由 |
|---|---|---|
| **PII 识别：NER vs 纯值模式** | 上游 `pii-processor` 依赖 `spacy>=3.8.2` + `presidio-analyzer==2.2.358`，需额外下载 NLP 模型权重，属重运行时 | **只移植"值模式匹配"那一遍，不引入 NER**。本平台已有列名启发式，值模式已能覆盖手机号/邮箱/身份证等结构化特征，收益/成本比更高 |
| **血缘解析器：collate-sqllineage vs sqlglot** | 上游 `collate-sqllineage==2.1.8` 为 base 依赖；本项目已有 `sqlglot>=25` | **以 sqlglot 为主解析器**，仅移植上游"多解析器回退 + 超时 + CTE 折叠"的**编排逻辑**；不新增 sqllineage 依赖 |
| **质量执行：SQLAlchemy 下推 vs Pandas** | 上游两者都支持 | **优先下推**，Pandas 仅在不支持时启用；`pandas` 目前只在本项目 `dev` extra 中，不得升为运行时依赖 |

## 3. 约束（Constitution）

以下为不可协商项，所有 FR 必须在其内求解：

| # | 约束 | 来源 |
|---|---|---|
| C1 | **存储不兼容、边界兼容**：内部用自有关系模型，对外交换用 OpenMetadata schema，经适配层转换 | ADR-8（`design/03`） |
| C2 | **L3 不修改 L1**：新增能力全部落在 `platform/`（L3），不得改动 `schema/`、`core/`（L1）；通过继承/组合/插件实现 | ADR-9（`design/04`） |
| C3 | **只读平台**：平台不提供任何写业务库能力；采样/画像必须通过只读账号执行 | `design/FE-00` §1.2.6 |
| C4 | 技术栈锁定：Python 3.10+ / FastAPI / SQLAlchemy 2.0 / PostgreSQL；前端 React 18 + antd 5 + React Query + zustand + `@xyflow/react`（已装） | `pyproject.toml`、`web/package.json` |
| C5 | 列表强制 keyset 游标分页，禁深 OFFSET | ADR-5 |
| C6 | **降级可视**：未上线能力显示"不可用"，不报错、不隐藏 | `design/FE-00` §1.2.4 |
| C7 | **上游 `ingestion/` 模块为 Collate Community License v1.0，不是 Apache-2.0**（仅仓库根 `LICENSE` 是 Apache-2.0）。该协议含 Excluded Purpose 排他条款，限制"提供与 Collate 产品竞争的在线服务"。**移植前必须取得法务结论（OQ-0）；结论未出前不得进入实施** | `ingestion/LICENSE:1-45`；`LICENSE:1` |
| C8 | 测试覆盖：现有 754 个单测为基线，新增能力须同标准覆盖 | `README.md` §测试覆盖 |

## 4. 用户场景

| 角色 | 场景 | 今天 | 迁移后 |
|---|---|---|---|
| 数据分析/业务 | 判断某张表能不能用 | 只能看字段类型与注释，看不到数据分布，只能自己去写 SQL 探查 | 打开表详情即见列级统计与分布直方图、空值率、枚举值样例 |
| 数据分析/业务 | 找一张不知道名字的表 | 必须先知道表名才能搜 | 搜索结果旁有分级/类型/数据源/负责人计数，可逐级收敛 |
| 数据平台/DBA | 评估一次改表的影响面 | 血缘功能默认关闭，无页面 | 血缘常开，可展开下钻，复杂视图/CTE 也能解析 |
| 数据治理/合规 | 输出敏感资产清单并复核 | 自动分级跑完即结束，结果只能筛选，人工无法批量修正 | 分级带置信度与命中依据，可按置信度区间批量复核 |
| 数据治理/合规 | 追溯"三个月前这字段是几级" | 无留痕 | 详情右侧版本时间线可回溯 |
| 安全审计 | 判断一次质量失败的影响 | 质量结果不落库，无从追溯 | 质量用例含失败行样本与成功率趋势 |
| 数据平台/DBA | 判断一次扫描是否真的失败 | 部分失败显示为整体失败 | 任务具有"部分成功"中间态与步骤级成功率 |

## 5. 功能需求

优先级：**P0** = 释放已有数据（数据/模型/组件现成，只差执行器或页面）；**P1** = 补能力闭环；**P2** = 体验与深度。

> **本文档为总纲，FR-M1~M9 不构成单一交付批次。** 各组已拆为独立 spec（`05-1` ~ `05-4`，见 §11.1），独立验收、独立回滚、可独立延后。下表用于对齐全景，开发工单以拆分后的 spec 为准。

### FR-M1 采样与列级画像（P0）⭐ 阻塞

**为什么是阻塞项**：F1/F2/F3 表明这是全平台唯一"两侧就绪、中间空缺"的能力，且下游 FR-M2 完全依赖它。

| # | 需求 | 借鉴来源（OpenMetadata） |
|---|---|---|
| FR-M1.1 | 采样比例按表行数**自动分档递减**，无需用户配置；小表全量，大表降采样 | `ingestion/src/metadata/sampler/config.py:258` `get_tiered_sample` |
| FR-M1.2 | 采样以 **SQL 下推**执行，优先利用库内 `TABLESAMPLE` / 分区裁剪；仅在不支持时退化为随机取模 CTE | `sampler/sqlalchemy/sampler.py:168-287`；各库覆写如 `sampler/sqlalchemy/snowflake/sampler.py:37` |
| FR-M1.3 | 行数估算优先读系统表统计信息，**失败才退化为 `COUNT(*)`** | 同上 |
| FR-M1.4 | 列级统计至少覆盖：行数、空值数/率、唯一值数、最小/最大、均值、标准差、分位数 | `profiler/processor/default.py:26-55`；`profiler/orm/functions/median.py:29-108` |
| FR-M1.5 | 分位数在各方言下优先使用库的近似函数，无近似函数时用精确函数 | `profiler/orm/functions/median.py` 的 `percentile_cont` / `approx_percentile` 覆写 |
| FR-M1.6 | 数值列生成分布直方图，桶数按数据自适应并**有上限**（避免大宽表产生巨量桶） | `profiler/metrics/hybrid/histogram.py:65-134` Freedman–Diaconis → Sturges 退化 → 封顶 |
| FR-M1.7 | 支持按数据源/库/schema/表三级配置**采样列白名单与黑名单**，以及采样开关 | `sampler/config.py:236-255` `get_include_columns` / `get_exclude_columns` |
| FR-M1.8 | 画像结果写入既有画像表并**保留历史快照**，可查某表任意历史时点的画像 | `storage/models_governance.py:26,143` |
| FR-M1.9 | 画像作业接入既有任务编排（触发方式、并发上限、重试、取消、耗时记录） | `platform/orchestration` |

**验收标准**
- AC-1.1：对行数 ≤ 阈值的表执行画像，采样比例为全量；超过阈值的表按分档自动降采样，且降采样比例可在任务日志中查到。
- AC-1.2：对一个含数值/字符串/日期/空值混合列的 PostgreSQL 表，产出的列级统计中，空值率与唯一值数与直接查询该表的结果一致（全量表要求精确一致，采样表允许偏差并在结果中标记 `sampled=true`）。
- AC-1.3：任一列的直方图桶数不超过规定上限。
- AC-1.4：画像执行期间对目标库的查询均为只读语句；使用只读账号可完整跑通。
- AC-1.5：连续两次画像后，可查询到两次历史快照及差异。

### FR-M2 画像可视化（P0）

**为什么紧跟 M1**：F4 + F5 —— 图表库已装未用、profile 路由为占位页，M1 落地后若无呈现层，产出仍然只有 API 消费者能用。

| # | 需求 |
|---|---|
| FR-M2.1 | 表画像页：表级概览（行数、列数、空值率分布）+ 列级统计列表，列可展开看直方图 |
| FR-M2.2 | 直方图支持"数值分布"与"字符串长度分布"两种口径 |

### FR-M6 分类分级：值模式验证与置信度（P1）

**为什么**：F8 + F11 —— 现有分级只有列名启发式，误报会直接进下游策略（`product-benchmark-roadmap.md` 反模式警示）；且 `product-benchmark-roadmap.md` 判断一要求"保住自动分级，不要推翻重做"，因此本需求是**增强**而非**替换**。

| FR-M6.2 | 每条判定**输出置信度与命中依据**（列名命中 / 值模式命中 / 两者同时命中） | 同上；`pii/scanners/column_name_scanner.py:27-80` |
| FR-M6.3 | 提供置信度阈值配置；低于阈值的判定标记为"待复核"而非直接生效 | 同上（默认阈值 0.1） |
| FR-M6.4 | 对高基数且明显无模式的列（如主键）**跳过值模式扫描**，控制开销 | 同上（相对基数 < 1% 跳过） |

| FR-M6.6 | 分级结果按级别分级审批：低级免审直接生效，高级走既有审批流 | `product-benchmark-roadmap.md` §3.3；既有 `approval_request` 表 |

- AC-6.3：低于阈值的判定进入"待复核"队列，且可批量确认。
- AC-6.4：既有"扫描后自动分级、新字段自动获得级别"的行为**不被破坏**（回归要求）。
- AC-6.5：**分级任务执行期间，对业务库发起的查询数量与关闭值模式验证时完全相同**（证明未新增取数）。

## 8. 边界情况（Edge Cases）

| # | 情况 | 期望行为 |
|---|---|---|
| E1 | 表行数为 0 | 画像成功返回空统计，不报错 |
| E2 | 单表列数极多（宽表） | 按列白/黑名单与列数上限裁剪；超限部分标记未采集 |
| E3 | 列全为空值 / 唯一值等于行数 | 分位数与直方图标记为不适用，不产生误导性图表 |
| E4 | 数据源不支持 `TABLESAMPLE` | 自动退化为随机取模采样，并在结果中标记采样方式 |
| E5 | 系统表统计信息不可用 | 退化为 `COUNT(*)`，并记录降级原因 |
| E6 | 画像执行中目标表被删除或权限被回收 | 任务失败并给出可操作原因，不重试打爆 |
| E7 | 采样样本恰好未命中敏感值 | 判定置信度低 → 进入待复核，而非判定为"非敏感" |
| E8 | 同一表被并发触发两次画像 | 幂等，后者复用前者结果或直接排队，不产生重复快照 |
| E9 | facet 维度值过多（如 owner 上千） | 按计数排序取 Top N，提供展开；不做无限列表 |
| E10 | 血缘 SQL 中包含临时表/动态 SQL | 折叠或标记为不可解析，不产生孤立节点 |
| E11 | 质量用例的失败行样本含敏感数据 | 按脱敏策略处理后再展示 |
| E12 | 上游 OpenMetadata schema 演进导致字段变化 | 适配层按版本分支处理；未知字段忽略（C1） |
