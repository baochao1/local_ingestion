## Verdict

事实基线扎实、约束与排除项写得比多数需求文档都清楚，但它目前是「一份迁移总纲 + 四份独立特性」被压成了一次决策：读者走完 §1 的问题陈述，仍无法必然得出 §11 的排期结论，因为中间缺了「价值 × 成本」排序，也缺了对「为什么不直接用上游包」这一首要反对的回应。

---

## Major findings

- **1. 未回答首要反对：为什么不直接依赖上游实现。**
  这是评审者看到"移植 OpenMetadata 画像/质量/血缘"时的第一反应——既然上游是 Apache-2.0 的 Python 包，为何不 `pip install openmetadata-ingestion` 直接调用，而要自己重写？文档在 A2 里只写了一句"不引入重型运行时依赖"作为**结论**，没有给出论证：依赖体积、Python 版本约束、SQLAlchemy 版本冲突、上游 `metadata` 包与本项目 `schema` 模型的语义冲突（ADR-8 明确二者存储模型不同）、长期维护负担。
  后果：全文 FR-M1/M5/M6 的"重写"决策悬空，任何一个评审者都可以用这一条推翻整个 P0。

- **2. 范围过大，混淆了"总纲"与"可批准单元"。**
  9 个 FR 组横跨后端算法、前端可视化、实体模型、任务编排四类工作，且 P0 内的 FR-M1/M2/M3/M4 **彼此无依赖关系**却共享一个排期。这带来三个具体问题：无法独立验收、无法独立回滚、任一受阻会拖住其余三条。
  Spec Kit 的粒度约定是一个 feature 一份 spec；本文档实际包含了 4 个 feature。

- **3. 成功标准在度量"产出量"而非"结果量"，落回了自己批评的陷阱。**
  §1.1 明确批评本平台"分级算出来了只能用来筛选 = 精美报表"。但 SC-2 是"画像覆盖率"、SC-5 是"占位路由激活比例"——这两个指标衡量的都是**东西做出来了**，不是**东西被用起来了**。若按此验收，迁移完成但业务价值仍未产生的情况会被判为成功。
  同类问题：SC-3「facet 使用占比」无目标值，不可验收。

- **4. 存在不可验收的验收条件。**
  AC-3.3 要求 facet 引入后 P95 退化"不超过约定阈值"，但 OQ-3 说阈值待压测；NFR-M2 同样写"阈值待压测确定"。一条验收条件引用了一个尚不存在的数。要么给基线值，要么改为"相对上线前不超过 X%"的相对指标。

- **5. FR-M6 与约束 C3（只读平台）存在未解冲突，但已排进 P1。**
  值模式验证本质上要读取业务数据内容——这与"平台不写业务库"不同，是**读敏感数据**，且比采样画像更进一步（画像是统计聚合，值模式是逐值匹配）。文档仅在 OQ-4 挂了一个问题，却在 §11 已把 FR-M6 放进 P1。合规风险被"记录在案"而非"解决"。更严重的是 R-M2 声称"默认只扫描已采样样本，不新增取数"——**这条在 FR-M6 正文里根本没有写成需求**，读者在需求章节看不到这个约束。

- **6. 与既有需求基线的关系未声明。**
  `01-product-requirements.md` / `04-requirement-review.md` 已有 FR-1~FR-16，覆盖分类分级、质量、检索、编排等域。FR-M5（质量用例）、FR-M6（分级）、FR-M9（编排）**是否存在与既有 FR 的重复或冲突**，文档未做映射也未声明"本 spec 优先级更高"。仅靠 §头部一句"FR-M\* 独立命名空间"不足以解决语义冲突——编号不冲突不代表需求不打架。

## Flow and organization

- **§2.1 目标 / §4 场景 / §5 需求三处映射靠读者自己拼。** G1~G8、角色场景、FR-M1~M9 三张表内容高度相关但没有交叉引用。建议在 FR 表头直接标注对应场景行与 G 编号。
- **§9 假设与 §1.2 事实重复。** A3（采样 SQL 与画像表已具备）与 F2/F3 说的是同一件事，中间隔了 8 节，读者会怀疑是不是有新信息。
- **§9 A / §10 OQ / §12 R 三表存在重叠。** A4 与 OQ-4（值模式读数据）、A6 与 OQ-3（facet 阈值）、R-M2 与 OQ-4 三处分述同一件事。风险表里已经写了"缓解措施"的问题，又出现在"待澄清"里，读者无法判断它到底是要决策还是要执行。
- **§8 Edge Cases 12 条无分级。** 其中 E4（不支持 TABLESAMPLE 时退化）直接影响 FR-M1.2 的实现选型，属于**设计约束**；而 E11（失败行含敏感数据）属于展示策略。混在一张平表里，阻塞级别的信息被淹没。
- **缺一节"与既有文档/模块的关系"。** 读者需要知道 FR-M4 与 MOD-07、FR-M6 与 MOD-05、FR-M5 与既有 quality 模块是覆盖还是增强，当前只能靠目录名猜。

## Objections and trade-offs

- **未给出"价值 × 成本"排序依据。** §1.3 用"两侧就绪、只缺执行器"论证 Profiler 优先，这个理由成立，但它只证明了**成本低**，没有证明**价值最高**。而 F11（分级结果无业务出口）与 `product-benchmark-roadmap.md` 判断三，指向的价值缺口恰恰在 FR-M6 而非 FR-M1。缺一张排序表，读者无法从问题走到排期。
- **facet 的技术选型只给结论未给论证。** A6 一句"关系库聚合可满足"承载了 FR-M3 的成败，而这是本 spec 里唯一可能被迫引入新基础设施的点（§2.2 又把 ES 列为非目标）。若压测不成立，FR-M3 无退路。
- **FR-M1.1 已按"照搬上游分档"写正文，OQ-1 却还挂着。** 需求正文不应先于决策落地。
- **FR-M9 独立成组显得凑数。** 4 条需求、本质是 FR-M1.9 的附属（"部分成功态"服务于画像/质量作业的结果展示）。独立编号会让人误以为是与 M1 平级的工作量。
- **R-M4（不同步形成新分叉）有风险无机制。** 写了"记录基线版本、只移植算法"，但既有的 `upstream-drift` CI job（`design/04` §7.3）**尚未建立**，R-M3 自己也承认这点。两个风险的缓解措施都依赖一个未完成的前置项，却没把它列进 P0 的准入条件。

## Conciseness and paragraph quality

- FR-M5 / FR-M6 / FR-M7 的「为什么」段落在重述 §1.2 已列的事实（F9 / F8+F11 / F6+F7）。建议改为引用事实编号："依据 F9"即可，省三段。
- §7 Success Criteria 中 SC-2 与 SC-5 措辞冗余（"覆盖率"与"激活比例"可合并为一条"既有资产被激活的比例"）。
- §9 假设表 7 条中，A1（许可证）、A5（图表库二选一）对需求内容无影响，属于实施期决策，可移入附录。
- §5 中"借鉴来源"一列混杂了 OpenMetadata 文件路径与"——"（无来源）两种值，读者会追问无来源条目的依据是什么。

## Suggested fixes

1. **新增「备选方案与取舍」章节**，正面论证为什么不直接依赖 `openmetadata-ingestion`（依赖体积 / Python 与 SQLAlchemy 版本约束 / 与自有存储模型的语义冲突 / 长期维护），并给出"先直接依赖、后逐步替换"这一折中方案的评估。这是批准本文档的前置条件。
2. **拆分或显式降级为总纲**。建议：FR-M1+M2（画像）独立为可批准单元，FR-M3、FR-M4、FR-M5+M6 各自独立；本文档保留为总纲并明确"各组独立验收、独立回滚、可独立延后"。
3. **给 FR-M6 一个不依赖读取业务数据的降级方案，并把"仅复用已采样样本、不新增取数"写成正文需求**（而非只在 R-M2 出现）。同时把 OQ-4 从"待澄清"提升为"P1 准入门禁"。
4. **修掉不可验收项**：AC-3.3 / NFR-M2 补基线值或改为相对指标；SC-3 补目标值；SC-2 / SC-5 从产出量改为使用量（如"画像页月活资产数""因画像避免了多少次人工探查"）。
5. **新增「与既有需求基线的关系」一节**，逐条声明 FR-M5/M6/M9 与 FR-1~FR-16、MOD-05/MOD-07 是增强、覆盖还是无冲突，并给出冲突时的优先级规则。
6. **合并 §9/§10/§12 的重叠项**，Edge Cases 标注阻塞级别（设计约束 vs 展示策略），把 A1/A5 移入附录。
7. **补"价值 × 成本"排序表**，让读者能从 §1 的问题陈述走到 §11 的排期结论；把 CI 边界检查（`boundary-check` / `upstream-drift`）列入 P0 准入条件，使 R-M3/R-M4 的缓解措施落地。
