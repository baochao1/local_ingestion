## 1. 审核结论

现有 FR-1 ~ FR-10 覆盖了七大业务功能与后续补充的采样、分类分级，**业务功能域基本完整**。但按「可交付产品」而非「功能列表」的标准审核，存在两类缺口：

1. **模块级缺口**：有 6 个产品化必需的能力域完全没有需求条目（检索、任务编排、身份稳定、业务元数据、平台运维、开放集成）
2. **模块内缺口**：9 个已有功能缺少支撑其闭环的次级需求

其中 **FR-12 任务编排**与 **FR-13 实体身份稳定**属于**阻塞级**——前者决定多实例部署下任务是否会重复执行，后者决定版本 Diff 与血缘的正确性。

## 2. 模块级缺口（新增 FR-11 ~ FR-16）

### FR-11 元数据检索与目录 ⭐ 阻塞

**为什么是缺口**：「找表、看字段、判断能不能用」是元数据平台最高频的场景，但现有需求中没有任何条目描述它。此前的讨论只在设计文档里涉及索引方案，`01` 需求文档完全缺失。没有检索，前面所有采集与治理的成果用户拿不到。

**需求要点**：
- FR-11.1 **全局搜索**：按表名/字段名/描述模糊检索，支持前缀与子串匹配
- FR-11.2 **多维筛选**：数据源、库、schema、表类型、分级、标签、负责人、是否含敏感字段
- FR-11.3 **排序与游标分页**：按名称/更新时间/分级排序；keyset 分页（NFR-1）
- FR-11.4 **资产详情视图**：表详情聚合字段列表、画像、标签、血缘摘要、近期变更
- FR-11.5 **资产概览统计**：数据源/库/表/字段总量、分级分布、敏感资产占比、质量分布
- FR-11.6 **字段级检索**：按字段名/类型跨库检索（千万级字段上的核心能力）
- FR-11.7 **搜索结果受限时的引导**：结果超上限时提示收窄条件（见设计文档 §7.3）

### FR-12 任务编排与调度 ⭐ 阻塞

**为什么是缺口**：现有 `APScheduler`（`engine/scheduler.py:78-84`）是**进程内**调度器。产品化后必然涉及多实例部署，届时同一任务会被多个实例重复执行。同时，扫描 → Diff → 告警的链式依赖、失败重试、并发控制均无需求条目。

**需求要点**：
- FR-12.1 **任务类型统一**：扫描 / 采样 / 画像 / 分级 / 血缘 / 权限采集，统一任务模型
- FR-12.2 **触发方式**：手动触发、定时（cron/interval）、事件触发（扫描完成后自动触发 Diff）
- FR-12.3 **多实例防重**：分布式锁或任务认领机制，保证同一任务仅被一个实例执行
- FR-12.4 **并发控制**：全局并发上限 + 每数据源并发上限（防打爆生产库）
- FR-12.5 **任务生命周期**：排队 / 运行 / 成功 / 失败 / 取消 / 超时，支持手动取消
- FR-12.6 **重试与退避**：可配重试次数与退避策略
- FR-12.7 **任务编排**：任务间依赖声明与串行/并行编排（扫描 → Diff → 通知）
- FR-12.8 **任务可观测**：历史记录、执行日志、耗时、失败原因

### FR-13 实体身份稳定与改名检测 ⭐ 阻塞

**为什么是缺口**：现有模型以 `fqn`（全限定名）作为实体标识（`schema/data/table.py:46`）。一旦表或字段改名，FQN 随之变化，平台会判定为「删除一张表 + 新增一张表」：

- 版本 Diff 产生误报的删/增事件
- 血缘边断裂（旧 FQN 的上下游关系丢失）
- 人工标注的标签、业务描述全部丢失

这是元数据平台的经典难题，现有需求完全未涉及。

**需求要点**：
- FR-13.1 **稳定内部标识**：实体 ID 与 FQN 解耦，FQN 变化不影响内部 ID
- FR-13.2 **表改名检测**：基于结构相似度（字段集合重合度）识别改名，而非判为删+增
- FR-13.3 **字段改名检测**：同表内基于类型 + 位置 + 名称相似度识别
- FR-13.4 **改名确认**：低置信度改名标记待确认，支持人工确认或驳回
- FR-13.5 **孤儿实体处理**：源端已删除的实体标记待确认，保留历史与血缘，支持确认删除或恢复
- FR-13.6 **历史 FQN 留存**：保留曾用名，支持按曾用名检索

### FR-14 业务元数据与术语表

**为什么是缺口**：现有 `tags: List[str]`（`table.py:23,57`）与 `owner: Optional[str]` 只能承载零散字符串，无法支撑「业务含义」。分类分级解决的是**安全维度**（敏感到什么程度），但用户还需要**业务维度**（这张表是干什么的、字段什么含义、归属哪个业务域）。二者不可混同。

**需求要点**：
- FR-14.1 **业务术语表**：术语/指标/业务域的维护与关联
- FR-14.2 **业务描述**：表与字段的业务含义（与技术描述分离）
- FR-14.3 **业务别名**：业务侧惯用名，支持按别名检索
- FR-14.4 **业务标签**：与分级标签（安全维度）分离存储与展示
- FR-14.5 **归属**：业务负责人 + 技术负责人（与平台账号关联，非纯字符串）

### FR-15 平台运维与可观测

**为什么是缺口**：现有 `observability/` 覆盖了指标与健康检查，但缺少产品化运维需求：数据保留清理、备份恢复、平台审计。

**需求要点**：
- FR-15.1 **平台健康**：数据库、调度器、连接器池、分区状态
- FR-15.2 **任务指标与告警**：扫描/采样/画像等任务的成功率、耗时、失败告警
- FR-15.3 **数据保留任务**：快照、样本、审计日志按保留策略自动清理
- FR-15.4 **分区自动预建**：按月分区的自动创建与过期 DROP
- FR-15.5 **平台审计日志**：采样、导出、凭据变更、人工标注等关键动作留痕
- FR-15.6 **备份与恢复**：元数据库备份策略与恢复演练要求

### FR-16 开放与集成

**为什么是缺口**：项目源自 OpenMetadata 生态（`pyproject.toml:4`、`README.md:160`），但未定义与外部系统的边界；同时对外集成能力（事件推送、导出）虽有 `integrations/webhook.py` 实现，却无需求条目。

**需求要点**：
- FR-16.1 **OpenAPI**：完整 API 文档与版本管理
- FR-16.2 **元数据导出**：资产清单、敏感资产清单、变更报告导出
- FR-16.3 **事件对外推送**：变更、分级结果等事件通过 Webhook 推送外部系统
- FR-16.4 **与 OpenMetadata 的关系界定**：明确是独立产品还是兼容/对接，避免定位摇摆
- FR-16.5 **外部血缘导入**：支持从 Airflow/DolphinScheduler 等调度系统导入血缘

## 6. 对排期的影响

原 `03-roadmap` 八阶段需调整：

1. **FR-12 任务编排应前置为阶段一的一部分**。它是所有任务型模块（扫描/采样/画像/分级）的公共底座，比采样更基础。否则各模块各自实现调度，必然重复且不一致。
2. **FR-11 检索应从「隐含在持久化里」提升为独立阶段**。它是用户唯一直接触达的界面，业务价值最高之一，建议在阶段一之后立即排入（可与版本 Diff 并行）。
3. **FR-13 身份稳定应并入阶段一建模**（`entity_alias` 历史名表 + 稳定 ID 策略），否则阶段二的版本 Diff 会产出大量改名误报。
4. **FR-14 / FR-16 属增强**，排入 P2 阶段。
5. **FR-15 运维**与阶段一并行建设。
6. **OpenMetadata 兼容分层（L1 上游同步区 / L3 本地扩展区）须在阶段一划定**。若先开发后分层，L3 代码会侵入 L1，后续上游同步将产生大量冲突，最终被迫放弃同步。适配层（L2）可随 MOD-02 落地。

调整后的排期见 `03-roadmap-and-open-questions.md`（后续同步更新）。
