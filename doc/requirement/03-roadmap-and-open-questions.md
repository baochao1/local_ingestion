## 1. 排期原则

1. **存储先行**。数据模型决定所有下游模块形态，模型不稳就并行开发必然返工。
2. **严格按依赖排序，不为功能编号顺序让路**。采样（FR-8）是画像（FR-5）与分类分级（FR-9）的共同前置；但版本 Diff（FR-3）**仅依赖持久化，与采样无依赖关系**，不应被采样阻塞。
3. **同依赖层级下，投入产出比优先**。优先做复用现有资产、投入小、客户感知强的能力（版本 Diff + 变动告警即属此类）。
4. **每阶段有可验收产物**，避免长周期无产出。
5. **每阶段结束时回归**已知缺陷与测试基线。

## 2. 依赖关系

```
                        阶段一 持久化与地基（阻塞一切，快照表在建模时一并落地）
                              │
        ┌─────────────────────┼─────────────────────┬──────────────────┐
        ↓                     ↓                     ↓                  ↓
阶段二 版本Diff+变动      阶段三 采样引擎        阶段六 血缘        阶段七 账号权限
(FR-3 + FR-7)            (FR-8)                (FR-4)             (FR-6)
仅依赖快照表               │                     独立性最强          相对独立
投入小、感知强      ┌──────┴──────┐            可全程并行
                    ↓             ↓
            阶段四 画像+质量  阶段五 分类分级
            (FR-5)          (FR-9)
                                   │
                                   ↓
                        阶段八 平台账号体系（FR-10）
```

**关键**：阶段二与阶段三**无依赖关系，可并行**。版本 Diff 只依赖快照表，不必等采样引擎。
血缘（阶段六）仅依赖持久化，可全程并行，不受阶段二~五进度影响。

## 3. 阶段划分

> **与初始五步路径的关系**：本路线沿用初始五步——`持久化 → 版本Diff+变动告警 → 画像 → 血缘 → 权限+RBAC+前端`。
> 因后续新增 **FR-8 采样**与 **FR-9 分类分级**两项需求，在第三步位置插入「阶段三 采样引擎」与「阶段五 分类分级」。
> 其余顺序与初始路径一致。**v1.1 修正**：版本 Diff 曾一度被排到采样之后，实为按功能编号顺序排期所致——它并不依赖采样，现已回归第二阶段。

### 阶段一：持久化与地基（P0）

**目标**：让元数据真正落库，消灭内存存储，稳定数据模型。

| 任务 | 说明 |
|---|---|
| T1.1 修复已知缺陷 | `cli/commands/scan.py:142` 导入错误；CORS 收紧（`api/app.py:106`） |
| T1.2 引入 Alembic | 迁移管理，模型变更可追溯 |
| T1.3 核心表建模 | `datasource` / `catalog_*` / **快照表与 `change_event`（阶段二依赖，须本阶段一并落地）**，含索引与分区设计 |
| T1.4 泛化 `SinkConnector` | 解耦 `FileSinkConfig`（`base.py:121`）与文件句柄（`file_sink.py:62`） |
| T1.5 实现 `PostgresSink` | 批量 upsert（`execute_values` + `ON CONFLICT`） |
| T1.6 迁移状态存储 | `FileStateStore`（`engine/state.py:160-217`）→ PG |
| T1.7 凭据加密 | 连接凭据加密落库与轮换 |
| T1.8 keyset 分页范式 | API 契约层统一，含列表/搜索/筛选 |
| T1.9 性能基准验证 | 以常规性能用例覆盖分页、批量写入、级联删除关键路径（**不做独立 PoC**） |
| T1.10 任务编排底座 | MOD-10：统一任务模型、多实例防重（PG advisory lock）、并发控制、重试与编排 |
| T1.11 实体身份稳定 | FR-13：稳定 ID + `entity_alias` + 改名检测基础（阶段二 Diff 依赖） |

**验收**：关键路径性能用例达标（列表查询 P95 < 500ms、批量写入分钟级、级联删除无长事务）；多实例下任务不重复执行；改名可被识别。
**风险**：R1（模型失误）在本阶段暴露。

> T1.10 任务编排须与持久化同批：若各模块各自实现调度与防重，后期收敛成本极高。
> T1.11 须在阶段一完成：否则阶段二的 Diff 会把改名误报为删+增。

### 阶段二：字段级版本 Diff 与变动告警（P0）

**目标**：让两次扫描之间的差异可见、可告警。这是**投入最小、客户感知最强**的能力。

**为什么排在第二**：仅依赖阶段一落地的快照表，与采样/画像/分级无依赖；且可大量复用现有资产——`checkpoint`（`pipeline/base.py:182-193`）、增量检测（`database_pipeline.py:283-356`）、告警通道（`integrations/webhook.py` HMAC 签名、`notifications.py` Email/Slack）。

| 任务 | 说明 |
|---|---|
| T2.1 快照写入 | 扫描完成即写 `table_snapshot` / `column_snapshot`（按月分区，阶段一建模） |
| T2.2 字段级 Diff | 以 `struct_hash` 前置过滤，仅对签名变化的表展开逐字段比对 |
| T2.3 破坏性变更识别 | 删表、删列、类型收窄、新增非空约束 |
| T2.4 变更分级 | breaking / structural / descriptive |
| T2.5 变更订阅 | 按数据源/库/表粒度（`notification_subscription`） |
| T2.6 通知去重与聚合 | 复用现有 Webhook/Email/Slack，避免告警风暴 |
| T2.7 变更视图与导出 | 变更列表、变更频次排行、稳定性评估 |

**验收**：能列出任意两次扫描间的全部字段级变更；破坏性变更被识别并准确通知到订阅方。
**说明**：与血缘联动的「变更影响面推送」依赖阶段六，后置补充。

### 阶段二并行项：检索与资产目录（MOD-09，P0）

**为什么单独列出**：`04` 需求审核发现 FR-11 检索是**模块级缺口**——它是用户唯一直接触达的界面，此前无需求条目。仅依赖阶段一的持久化，可与阶段二、阶段三并行。

| 任务 | 说明 |
|---|---|
| T2B.1 全局检索 | 表/字段模糊检索 + FQN 前缀（trigram + btree） |
| T2B.2 多维筛选 | 数据源/库/schema/类型/分级/标签/负责人 |
| T2B.3 资产详情聚合 | 结构+画像+分级+变更+血缘摘要（并发取数，禁 N+1） |
| T2B.4 概览统计 | 预计算 + 缓存 |
| T2B.5 业务元数据 | 术语表、业务描述、别名、`business.*` 标签 |

**验收**：千万级字段检索 P95 < 500ms；详情聚合接口并发取数；业务标签与安全标签互不覆盖。
**降级要求**：MOD-07（血缘）、MOD-08（授权）、MOD-11（权限）未上线时，本模块须正常提供服务。

### 阶段三：数据采样引擎（P0，与阶段二可并行）

**目标**：安全可控地获取业务数据样本，为画像与分类分级提供输入。

| 任务 | 说明 |
|---|---|
| T3.1 采样方言抽象 | PG / Snowflake 原生 `TABLESAMPLE`；MySQL 无此语法，走主键点查策略 |
| T3.2 `StatSampler` | SQL 下推聚合（不拉全量行） |
| T3.3 `ValueSampler` / `RowSampler` | 值样本与样本行 |
| T3.4 采样策略配置 | 采样率、上限、超时、并发、大表熔断 |
| T3.5 生产保护 | 只读账号校验、低峰调度、限流 |
| T3.6 安全机制 | 敏感列黑名单、脱敏、加密、TTL、审计 |
| T3.7 能力位 | `SourceConnector` 增加 `supports_sampling` |

**验收**：对大表采样不影响生产库负载；采样值默认不落库；黑名单列不被采样。
**风险**：R2（拖垮生产库）、R3（PII 泄露）。本阶段须做生产库影响评估。

### 阶段五：分类分级（P1）

| 任务 | 说明 |

## 5. 待确认问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| Q1 | FR-6 口径：扫描业务库账号权限，还是平台自身 RBAC？ | 决定阶段七与阶段八范围与优先级 | 建议先做前者（数据源侧权限治理），平台 RBAC 视部署形态再定 |
| Q2 | 分级标准是否已有既定规范（如 L1–L4）？ | 影响分级模型设计与规则库 | 建议先实现可配置模型，预设一套四档默认值 |
| Q3 | 千万级是目标上限还是起步规模？是否需考虑亿级？ | 影响分区策略与是否提前引入外部组件 | 建议按亿级做分区设计，按千万级做容量验证 |
| Q4 | 部署形态：SaaS 多租户还是私有化单租户？ | 决定租户隔离深度（是否所有表加 tenant_id） | 建议即便单租户也预留 tenant_id 字段，改造成本低 |
| Q5 | 元数据变更的实时性要求（分钟/小时/天）？ | 决定调度频率，是否需引入 CDC | 建议 MVP 按天级调度，实时性留到后续 |
| Q6 | 本期是否需要前端？ | 影响 API 契约设计与工作量 | 建议本期仅交付 API；前端另立项目 |
| Q7 | 采样是否允许访问生产库真实数据？有无合规审批要求？ | 决定阶段二能否开展 | **阻塞项**，须先确认；否则采样功能只能做元数据层推断 |
| Q8 | 是否需要支持非数据库数据源（Hive、Kafka、对象存储、BI 报表）？ | 影响连接器抽象设计 | 建议抽象层预留，实现排到后期 |
| Q9 | 血缘数据来源有哪些可用？是否有 ETL 调度系统（Airflow/DolphinScheduler）可对接？ | 决定血缘覆盖率，纯 SQL 解析覆盖有限 | 建议先做视图定义推导 + SQL 解析，再对接调度系统 |
| Q10 | 现有 `InMemoryDB` 与文件落盘是否已有外部依赖方？ | 影响迁移方式 | 建议保留文件 sink 作为可选输出，新增 PG sink 并行 |

> **Q7 为阻塞项**：若不允许采样访问生产数据，FR-8 需退化为「仅统计型下推聚合（不取样本值）」，FR-9 分类分级的采样回验能力将失效，误报率会显著上升。
