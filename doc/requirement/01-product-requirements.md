## 1. 产品定位

### 1.1 一句话定位

把现有的「数据库元数据摄取模块」升级为**企业级元数据治理平台**：统一纳管异构数据源，持续扫描并留存元数据，在元数据之上提供版本追溯、血缘分析、质量画像、分类分级、账号权限与变动告警能力。

### 1.2 为什么需要重新定位

当前仓库的自我描述是「Local Ingestion Module for OpenMetadata」（`pyproject.toml:4`），README 也明确其为「轻量级本地元数据摄取模块，支持本地开发和测试环境」（`README.md:3`）。其设计目标是**单次、本地、无状态地把元数据抽出来写进文件**，而非长期运营一个可查询、可追溯、可告警的资产库。

这个定位差异决定了产品化的核心矛盾：**摄取是一次性动作，治理是持续性状态**。所有需要「历史」「对比」「关联」「订阅」的功能，在现有架构上都不成立。

### 1.3 目标用户与场景

| 角色 | 核心场景 |
|---|---|
| 数据平台/DBA | 纳管全公司数据源；发现表结构变更；评估变更影响面 |
| 数据治理/合规 | 全量字段分类分级；输出敏感资产清单；权限合规审计 |
| 数据分析/业务 | 找表、看字段含义、看数据质量、看上下游依赖 |
| 安全审计 | 账号权限梳理、越权与过度授权识别、敏感数据访问审计 |

## 2. 现状基线（基于代码事实）

本节记录**实测**现状，用于评估工作量。注意：README 中的部分描述与代码不符，不可作为基线依据。

### 2.1 技术栈

Python 3.10+，FastAPI + SQLAlchemy 2.0 + APScheduler + Prometheus（`pyproject.toml:6-23`）。
无 Java/Gradle、无 Flyway/Liquibase、无 Elasticsearch、无图数据库、无任何 SQL 解析器依赖。

### 2.4 已知缺陷（产品化前须修复）

1. **导入错误**：`cli/commands/scan.py:142` 导入 `PostgreSQLSourceConnector`，但实际类名为 `PostgresSourceConnector`（`postgres.py:25`）→ `scan postgres` 必然 ImportError。
2. **文档失真**：README 宣称 ~354+ 测试（`README.md:156`），实际 25 个测试文件 / 145 个 test 函数，且 `tests/integration/` 目录不存在（`README.md:63`）。
3. **CORS 全开**：`api/app.py:106` 为 `allow_origins=["*"]`。
4. **类型映射硬编码**：各连接器各写一份映射（`postgres.py:329-393`），无方言抽象。

## 3. 功能需求

编号规则：`FR` = 功能需求。每个功能标注**现状基线**，用于判断净工作量。

### FR-1 数据源管控

**目标**：统一纳管异构数据源，管理连接、凭据、采集策略与生命周期。

**现状基线**：骨架 30%。有 5 种连接配置模型（`connection.py:35-124`）与 databases CRUD 路由（`api/app.py:180-206`），但存储为内存 dict。

**需求要点**：
- FR-1.1 数据源注册、编辑、启停、删除（删除须安全级联，见 NFR-2）
- FR-1.2 **凭据加密存储**，禁止明文落库或进配置文件；支持凭据轮换
- FR-1.3 连通性测试：保存前校验可达性与权限
- FR-1.4 采集策略配置：扫描范围（库/schema 黑白名单）、调度周期、采样开关、并发上限
- FR-1.5 采集只读化：强制使用只读账号，平台侧校验并拒绝具备写权限的连接
- FR-1.6 数据源健康度：最近扫描状态、耗时、失败原因、连通性趋势

### FR-2 数据扫描

**目标**：按策略持续抽取库/schema/表/字段元数据，支持全量与增量。

**现状基线**：最强项，60–70%。连接器、流水线、并行、checkpoint、增量、调度齐备。

**需求要点**：
- FR-2.1 全量扫描与增量扫描，增量须下沉到**字段级**（当前仅表级）
- FR-2.2 断点续跑，异常中断后可从 checkpoint 恢复（已有，需迁移到持久化状态存储）
- FR-2.3 扫描任务可观测：进度、吞吐、失败明细、重试
- FR-2.4 **方言抽象层**：统一管理类型映射与系统表查询，消除各连接器重复实现
- FR-2.5 新数据源扩展应通过插件机制接入，不改核心代码
- FR-2.6 补齐 SQL Server、BigQuery 连接器（配置已存在但无实现）

### FR-3 数据版本管理

**目标**：留存每次扫描的元数据快照，支持任意时点回溯与版本间差异比对。

**现状基线**：约 5%。仅有一个只比对 description 与列数的变更判断函数。

**需求要点**：
- FR-3.1 每次扫描生成快照，快照可回溯、可查询
- FR-3.2 **字段级 diff**：新增/删除/改名/类型变更/约束变更/顺序变更，而非仅列数比对
- FR-3.3 表级与库级变更视图（新增表、删除表、表更名）
- FR-3.4 快照保留策略与清理（保留窗口、按数量保留、按时间保留）
- FR-3.5 版本对比结果可导出

### FR-4 数据血缘分析

**目标**：构建表级与字段级血缘，支持上下游追溯与影响面分析。

**现状基线**：0%。无任何 SQL 解析能力与血缘代码。

**需求要点**：
- FR-4.1 **表级血缘**：解析 ETL 脚本、视图定义、SQL 日志获取
- FR-4.2 **字段级血缘**：字段到字段的映射关系
- FR-4.3 上下游追溯：指定深度的上游/下游展开
- FR-4.4 **影响面分析**：某表/字段变更时，评估下游受影响范围
- FR-4.5 环检测与展示（真实环境存在循环依赖）
- FR-4.6 血缘来源标注：视图定义推导 / SQL 解析 / 人工标注，并标注置信度

### FR-5 数据特性分析（数据质量）

**目标**：产出表与字段的数据画像，并按规则评估质量。

**现状基线**：规则校验 40%，画像 profile 5%。有 6 类质量规则与校验/报告引擎；`TableProfile` 为空壳模型。

**需求要点**：
- FR-5.1 **统计画像**：行数、空值率、唯一值数、最小/最大/均值/标准差、值分布
- FR-5.2 画像须由数据库侧聚合下推计算，禁止拉全量数据到平台计算（见 NFR-1）
- FR-5.3 质量规则执行：非空、唯一、值域、正则、参照完整性、自定义 SQL
- FR-5.4 质量评分与趋势：表/库级质量分，历史趋势
- FR-5.5 质量报告导出（复用现有 `reporter.py`）
- FR-5.6 画像与质量的采集周期独立于元数据扫描，避免拖慢扫描

### FR-6 账号权限分析

**目标**：梳理数据源侧的账号、角色与授权，识别过度授权与合规风险。

**现状基线**：0%。无账号/角色/权限模型。

**需求要点**：
- FR-6.1 采集库内账号与角色（MySQL `mysql.user` + `SHOW GRANTS`；PG `pg_roles` + `role_table_grants`；Snowflake `GRANTS_TO_USERS`）
- FR-6.2 权限矩阵：账号 × 库/表/字段 的授权视图
- FR-6.3 风险识别：超管账号、过度授权、长期未使用账号、无主账号、弱口令策略
- FR-6.4 权限变更追踪与告警
- FR-6.5 与分类分级联动：高敏资产（L3/L4）上的授权重点标注

> **待确认**：FR-6 指「扫描并分析业务库内的账号权限」，还是「平台自身的账号权限体系（RBAC）」？二者都需要，但优先级与工作量差异大。本文档按前者编写，平台自身 RBAC 列为 FR-10。

### FR-7 数据变动分析

**目标**：基于版本 diff 发现变更，主动通知受影响方。

**现状基线**：约 20%。有表级增量检测雏形与完整告警通道（Webhook/Email/Slack）。

**需求要点**：
- FR-7.1 变更事件定义与分级（结构性变更 / 描述性变更 / 破坏性变更）
- FR-7.2 **破坏性变更**识别：删表、删列、类型收窄、非空约束新增
- FR-7.3 变更订阅：按数据源/库/表粒度订阅
- FR-7.4 多渠道通知（复用现有 Webhook/Email/Slack）+ 通知去重与聚合
- FR-7.5 变更统计：变更频次的库/表排行，稳定性评估
- FR-7.6 与血缘联动：变更影响面推送给下游责任人

### FR-8 数据采样

**目标**：安全、可控地获取业务数据样本，支撑画像、分类分级验证与数据预览。

**现状基线**：0%。仅 `generateSampleData` 声明字段（`routes/schemas.py:52`）。

**需求要点**：
- FR-8.1 **统计型采样**：行数/空值/去重数/极值/均值/标准差，由数据库聚合下推
- FR-8.2 **值样本型采样**：字段 distinct 取值样例，供分类分级与质量校验回验
- FR-8.3 **样本行采样**：少量真实记录用于预览（须脱敏）
- FR-8.4 采样策略可配：采样率、上限行数、超时、并发上限、跳过阈值
- FR-8.5 **跨库方言适配**：PG/Snowflake 原生采样；MySQL 无 `TABLESAMPLE`，须走主键点查等替代策略
- FR-8.6 采样安全：只读账号、敏感列黑名单、采样后脱敏、样本加密与 TTL 清理、全程审计
- FR-8.7 **反向联动**：分类分级判定为高敏的列，自动停止采样并清除已有样本
- FR-8.8 样本值默认不持久化，仅在显式开启且有保留期时落库

### FR-9 元数据分类分级

**目标**：自动识别字段的业务语义类别与敏感等级，输出敏感资产清单。

**现状基线**：0%。现有 `tags: List[str]`（`table.py:23,57`）为纯字符串列表，无法承载来源与置信度。

**需求要点**：
- FR-9.1 分级标准可配（如 L1 公开 / L2 内部 / L3 敏感 / L4 核心），支持自定义
- FR-9.2 分类识别：手机号、身份证、邮箱、银行卡、地址、姓名等常见 PII
- FR-9.3 多策略识别：字段名词典 + 正则规则 + 数据类型启发式 + **采样值回验**
- FR-9.4 标签须携带元数据：`{名称, 来源: 规则/采样/人工, 置信度, 生效时间}`
- FR-9.5 **人工修正优先**：人工标注不被后续自动扫描覆盖
- FR-9.6 表级等级由其字段的最高等级聚合得出
- FR-9.7 引擎可独立重跑，规则迭代后无需触发全库重扫
- FR-9.8 敏感资产清单导出与合规报表

### FR-17 协作与流程（审批流 + 工单）

**目标**：补齐企业治理必需的「人在环（human-in-the-loop）」协作能力——资产发布 / 分类分级结果 / 敏感标注 / 删除等动作需责任人审批；数据问题与破坏性变更需可跟踪的工单闭环。对应 `MOD-12-governance.md`。

- FR-17.1 审批流：提交审批请求（资源类型/动作/发起人/审批人/优先级/理由）
- FR-17.2 审批决策：通过 / 驳回（含审批意见），决策不可重复、不可撤销重提需新单
- FR-17.3 审批范围：覆盖资产发布（publish）、分类分级结果（classify）、敏感标注（sensitive_tag）、删除（delete）
- FR-17.4 工单：创建数据问题 / 权限申请 / 其他工单，含优先级（P0–P3）、状态、负责人、SLA 到期
- FR-17.5 工单状态机：`open → in_progress → resolved → closed`，支持 `closed → in_progress`（重开）
- FR-17.6 工单分派与评论线程：可指派处理人，工单/审批均可追加评论与处理记录
- FR-17.7 自动建单：FR-7 破坏性变更被确认后，自动创建 `change_auto` 工单（P0，SLA 24h）跟踪影响面与下游依赖
- FR-17.8 审计留痕：所有审批决策与工单状态流转写入 `audit_log`（契约 C10），满足合规审计
- FR-17.9 集成：通过 `MOD-10` 的 Webhook/事件（FR-16）将审批/工单事件推送到 Jira / ServiceNow 等外部系统

> **售前说明**：审批流与工单是本平台对标 Alation / Collibra / OpenMetadata / DataHub 的关键协作能力，原 `§5.1` 将其列为「本期不做」，已在 MOD-12 全部实现（代码 + 接口 + 联动）。

### FR-10 平台账号与权限（待确认优先级）

- FR-10.1 平台用户体系与认证
- FR-10.2 RBAC：功能权限 + 数据权限（仅可见被授权的数据源/库/表）
- FR-10.3 多租户隔离
- FR-10.4 操作审计日志

## 4. 非功能需求

### NFR-1 性能与容量

| 项 | 要求 | 说明 |
|---|---|---|
| 元数据规模 | 支撑 **千万级**字段元数据 | 按 30–50 万表 × 30 列估算 |
| 查询响应 | 列表查询 P95 < 500ms；详情 < 300ms | 千万级数据量下 |
| 分页方式 | **强制 keyset（游标）分页**，禁用深 OFFSET | 深分页在千万行上不可接受 |
| 写入吞吐 | 全量扫描千万级字段须在分钟级完成 | 须批量 upsert，禁逐条 INSERT |
| 级联操作 | 禁止大结果集单事务级联删除 | 须软删除 + 异步分批清理 |
| 快照膨胀 | 快照表须分区，支持按分区快速清理 | 快照是增长最快的表 |
| 采样保护 | 采样不得影响生产库：只读账号、超时、并发上限、大表熔断、低峰调度 | 硬约束 |

### NFR-2 安全

- NFR-2.1 数据源凭据加密存储，支持轮换；日志中禁止打印凭据
- NFR-2.2 采样数据默认不落库；落库时加密并设置 TTL
- NFR-2.3 敏感列采样后即时脱敏；高敏列自动熔断
- NFR-2.4 平台 API 须认证；CORS 收紧到显式域名（当前为 `*`）
- NFR-2.5 所有敏感操作（采样、导出、凭据变更）留审计日志

### NFR-3 可扩展与可维护

- NFR-3.1 新增数据源、质量规则、分类规则、血缘解析器均应通过插件机制接入
- NFR-3.2 方言差异（系统表查询、类型映射、采样语法）统一收敛到方言抽象层
- NFR-3.3 数据模型变更须走迁移工具（建议 Alembic）管理

### NFR-4 可观测性

- NFR-4.1 复用现有 Prometheus 指标与告警框架，覆盖扫描/采样/分类分级/血缘各任务
- NFR-4.2 任务失败可定位到具体库/表/字段
- NFR-4.3 平台自身健康检查（现有 `observability/health.py` 扩展）

### NFR-5 数据质量基线（工程侧）

- NFR-5.1 补齐集成测试（README 声明的 `tests/integration/` 不存在）
- NFR-5.2 修复 `scan.py:142` 导入错误等已知缺陷
- NFR-5.3 关键路径（分页、diff、血缘递归、采样）须有性能回归测试

## 5. 范围边界

### 5.1 本期不做

- 数据脱敏执行、数据血缘的运行时采集（Agent 模式）
- 实时流式元数据变更捕获（CDC）
- 数据目录的协作能力（评论、认领）——**审批流与工单已在 MOD-12 实现，不在排除范围内**
- 数据资产计费/成本分析
- 机器学习驱动的分类识别（本期仅规则 + 采样回验）
- 前端（本期仅提供 API；前端另立项目）

### 5.2 明确排除的选型

- 不引入图数据库作为主存储（详见 `02-design-direction.md` ADR-2）
- 不引入 Elasticsearch 作为主存储（MVP 阶段，详见 ADR-3）
- 不引入 JVM 系 SQL 解析器（如 Calcite/ANTLR，运维成本高）
