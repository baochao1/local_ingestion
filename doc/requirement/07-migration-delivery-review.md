## 二、Major findings（必须点名的问题）

### 1. 三处"就绪但未接线"——最容易被误读为已上线

| 能力 | 已有什么 | 缺什么 |
|---|---|---|
| 质量（FR-M5） | `QualityService.run()` 能下推执行并落库；**已接入 `JobType.QUALITY` 编排触发**（本轮收尾） | 前端质量页触发入口 + 结果趋势可视化留待 UI 迭代 |
| 分级验证（FR-M6） | `evaluate_column()` 能算出等级与置信度 | **classification 服务未调用它**；且它需要"样本值"，而画像目前只存**聚合统计**，样本值通道尚未建立 |
| 血缘（FR-M4） | 已接线 ✅ | —（审核中发现的缺口，已在本次修复） |

**为什么重要**：这三处的测试都是绿的，读代码的人会以为功能可用。质量与分级尤其危险——分级误报会直接进下游策略，而"算法存在但没被调用"比"算法不存在"更容易被当成"已经防住了"。

### 2. `compute_facets` 忽略了 `type` 与 `sensitiveOnly`

函数内 `del type, sensitive_only` —— 这两个过滤**不参与分面统计**。若用户勾选"仅敏感"，分面计数仍是全量，与结果列表不一致（违反 FC2 的字面要求）。

影响有限（分面只统计 `catalog_table`），但属于已声明约束未被满足，必须显式记录而非静默。

### 3. FR-M6 的"不新增取数"靠签名保证，但也因此**没有样本来源**

`evaluate_column(samples=...)` 从签名上杜绝了取数（FR-M6.7），这是对的。但反过来说：画像目前不采集样本值，`samples` **没有生产者**。该能力要真正生效，需要画像侧增加"低基数列样本值采集"（受 `max_columns` 与体积上限约束）。

### 4. 画像页「立即采集」提交后不自动刷新

`onSuccess` 只弹提示，未失效查询缓存，用户需手动刷新才能看到结果（FR-M2 未明确要求，但体验上是断点）。

## 四、做得对的地方（值得保留的做法）

1. **测试抓到真漏洞**：集成测试发现 `_resolve_row_count` 在标识符校验**之前**就拼了 `COUNT(*)`，校验形同虚设。单测覆盖不到这类问题。
2. **不从 `app.routes` 判断路由**：fastapi 0.142 的 `_IncludedRouter` 会给出假阴性，改用 `app.openapi()`。
3. **不伪造血缘边**：血缘页只画直接上下游，因为闭包不含父子关系——按 depth 相邻层连边会凭空造边（E8）。
4. **不可筛选就置灰**：schema 分面置灰并说明原因，而不是给一个点了没用的入口。
5. **"不新增取数"写进签名**：FR-M6.7 由函数签名强制，而非靠注释承诺。
6. **既有 11 failed / 14 collection error 全部消除**：根因是 4 个 `pyproject` 已声明但环境缺失的依赖，不是代码缺陷。

---

## 五、建议的修复优先级

1. **给质量与分级接线**（或至少在 spec 里把状态从"完成"改为"服务就绪、待接线"）——否则状态被高估。
2. **补 `type` / `sensitiveOnly` 到分面过滤**，或在 facets.py 顶部显著标注该限制。
3. **画像侧增加受控的样本值采集**，为 FR-M6 提供 `samples` 来源。
4. **画像页采集成功后失效查询缓存**。
5. **执行 G3 基线压测**，让 NFR-M2 的 1.5 倍有参照。
6. FR-M7 / FR-M8.3 作为独立迭代排期。
