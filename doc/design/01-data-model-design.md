## 1. 设计约定

### 1.1 通用约定

| 项 | 约定 | 理由 |
|---|---|---|
| 主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 千万级下 BIGINT 比 UUID 省一半索引空间；`BY DEFAULT` 便于快照回填 |
| 业务主键 | `fqn`（fullyQualifiedName）唯一索引 | 与现有模型 `Table.fullyQualifiedName`（`schema/data/table.py:46`）对齐 |
| 时间 | `TIMESTAMPTZ`，统一 UTC 存储 | 避免时区歧义 |
| 软删除 | `deleted_at TIMESTZ NULL` | 支撑级联安全删除（见 §5.3） |
| 审计 | `created_at` / `updated_at` | 变更追踪基础 |
| JSONB 默认值 | `'{}'::jsonb` 非空 | 避免 NULL 判断分支 |
| 枚举取值 | `TEXT` + `CHECK` 约束 | 业务枚举易变，`ALTER TYPE` 无法删值，TEXT 更灵活 |
| 租户 | 全部业务表预留 `tenant_id`，默认 `0` | 即便当前单租户，预留成本极低（见 Q4） |

### 1.2 命名约定

- 元数据实体统一前缀 `catalog_`（`catalog_table` / `catalog_column`），避免与关键字 `table` 冲突
- 治理能力表按功能命名（`table_profile` / `lineage_*` / `entity_tag` / `change_event`）
- 索引命名：`idx_<表缩写>_<列>`，唯一索引 `uq_<表缩写>_<列>`

### 1.3 分级字段设计

分级需兼顾「可排序、可筛选」与「可自定义」：

- `grade_level SMALLINT`（1–9）：**有序，用于比较与索引**，如"等级 ≥ 3 的字段"
- `grade_code TEXT`：展示用，如 `'L3'`
- 二者映射由 `classification_tag` 配置定义

若只存 `TEXT`，按等级范围筛选（`BETWEEN`）将失效；若只存数字，则无法适配自定义分级名称。

## 3. 核心建模决策

### 决策 A：字段打散为行，同时在表级冗余 JSONB

**问题**：现有 `Table.columns: List[Column]`（`schema/data/table.py:51`）是嵌套结构。若整表 JSONB 化，字段级血缘、字段级分级、按列名/类型检索全部不可行。

**方案**：

| 存储 | 用途 |
|---|---|
| `catalog_column` 独立行 | 检索、join、打标、血缘、Diff —— 千万级，全部可索引 |
| `catalog_table.columns_json` JSONB | 详情接口一次读取，避免 30 行 join 放大 |

**代价**：双写一致性。做法——同事务内写入，以 `catalog_column` 为准，`columns_json` 为缓存；提供重建任务按 `table_id` 重刷。

**为什么不做列拆分到独立表 + 无冗余**：详情页会退化为 30 次 join，P95 无法达标。

### 决策 B：`catalog_column.children` 不打散

`Column.children`（`table.py:22`）表示嵌套类型（struct / array of struct）。此类结构：

- 占比极低（<1%）
- 打散会让表结构递归复杂化，且行数不可控
- 无独立检索/打标需求（分级跟随父字段）

故以 JSONB 存于 `children` 列。

### 决策 C：冗余 `datasource_id` 到 `catalog_table` / `catalog_column`

**理由**：

1. 按数据源批量操作（删除、重扫、统计）可避免 `column → table → schema → database → datasource` 四层 join
2. 千万行表上消除 join 收益显著

**代价**：数据源归属不变（业务上成立），无同步更新负担。

### 决策 D：画像每表一行 JSONB

`TableProfile` 的 `minValue / maxValue / mean / sum / stdDev` 本就是 `Dict[str, Any]`（`table.py:36-40`，per-column 语义），天然适配「每表一行 JSONB」。

此举把画像表从「千万行」降到「数十万行」，是决定性的量级优化。

### 决策 E：结构签名 `struct_hash`

**用途**：把字段级 Diff 从「逐字段比对」降为「签名比对」，同时支撑增量扫描的变更判定，替代现有仅比对 description 与列数的弱判断（`database_pipeline.py:358-376`）。

**定义**（字段级）：

```
struct_hash = md5(
  name | '|' | data_type | '|' | data_length | '|' | precision | '|' | scale
       | '|' | nullable | '|' | coalesce(default_value,'')
)
```

**定义**（表级）：

```
struct_hash = md5( 按 ordinal_position 升序拼接的所有字段 struct_hash )
```

**作用**：

- 增量扫描：签名未变则跳过后续处理
- Diff：签名变化才展开逐字段比对，定位具体变更类型
- 顺序变更会被捕获（拼接顺序参与哈希）

### 决策 F：标签结构化，`entity_tag` 与冗余列并存

现有 `tags: List[str]`（`table.py:23,57`）无法表达 `{名称, 来源, 置信度, 生效时间}`，也无法保证人工修正不被自动扫描覆盖（FR-9.5）。

**方案**：

| 存储 | 用途 |
|---|---|
| `entity_tag` 表 | 标签明细（来源、置信度、生效时间、过期时间）—— 多值检索 |
| `catalog_column.grade_level` / `grade_code` | **冗余**，供高频筛选直接走索引，避免 join 千万行 |
| `catalog_column.tags` JSONB | **冗余**，供详情展示与标签筛选（GIN） |

冗余列由引擎在打标事务内同步维护。

## 5. 分区策略

### 5.1 `catalog_column` MVP 不分区（重要决策）

| 考量 | 结论 |
|---|---|
| 数据量 | 1500 万行 ≈ 3–5 GB + 索引 3–5 GB，远未达分区阈值（业界通常 >5000 万行或 >100 GB） |
| 分区代价 | PG 要求**唯一约束必须包含分区键** → `UNIQUE(fqn)` 退化为 `UNIQUE(fqn, datasource_id)`；外键引用复杂度上升；`entity_tag` 跨分区 join 变慢 |
| 收益 | 主要为「删数据源时快速清理」，但软删除 + 分批清理（§5.3）已可满足 |

**结论**：MVP 不分区。**触发迁移条件**：单表 >5000 万行或 >50 GB，或单数据源删除成为高频操作。

**迁移路径**：使用 `pg_partman` 或手工「新建分区表 → 双写 → 回填 → 切换」，PG 支持 `ATTACH PARTITION` 在线挂载，无需长时间停机。

### 5.2 必须分区的表

| 表 | 分区键 | 粒度 | 理由 |
|---|---|---|---|
| `column_snapshot` | `snapshot_date`（DATE） | 月 | 每轮扫描 × 1500 万，增长最快 |
| `table_snapshot` | `snapshot_date` | 月 | 同上 |
| `change_event` | `detected_at` | 月 | 持续累积 |
| `audit_log` | `occurred_at` | 月 | 合规留存，量大 |
| `sample_value` | `sampled_at` | 月 | 便于 TTL 整分区 drop |

**为什么按月而非按 `scan_run_id`**：一个数据源每天一次扫描 × 数百源 → 一年数万个 `scan_run`，若按 `scan_run_id` LIST 分区会产生数万个分区，超出 PG 运维舒适区（分区数建议 < 1000）。按月分区则一年仅 12 个。

若单月数据量过大（如 `column_snapshot` 单月上亿），可降级为**按周**或**按天**，配置化决定。

**保留策略**：保留窗口外的分区直接 `DROP PARTITION`（秒级），而非 `DELETE`（千万行级长事务）。

### 5.3 级联删除：软删除 + 异步分批

**禁止** `ON DELETE CASCADE` 于 `catalog_column`（千万行单事务会导致长锁、WAL 爆写、复制延迟）。

**流程**：

```
1. UPDATE datasource SET deleted_at = now() WHERE id = $1;         -- 秒级
2. 异步任务：按 table_id 分批软删
     UPDATE catalog_column SET deleted_at = now()
     WHERE id IN (SELECT id FROM catalog_column
                  WHERE datasource_id = $1 AND deleted_at IS NULL
                  ORDER BY id LIMIT 5000);
     每批提交，批间加 sleep，可中断可续跑
3. 同法处理 catalog_table / catalog_schema / catalog_database / entity_tag
4. 物理清理：独立任务批量 DELETE（或快照类 DROP PARTITION）
```

**要点**：所有业务查询默认带 `WHERE deleted_at IS NULL`，索引为部分索引（更小）。

## 6. 索引策略

### 6.1 核心索引

| 表 | 索引 | 类型 | 支撑场景 |
|---|---|---|---|
| `catalog_table` | `(fqn, id)` | UNIQUE 部分（`deleted_at IS NULL`） | keyset 分页 + 唯一约束 |
| | `(datasource_id, fqn, id)` | btree 部分 | 按源筛选 + keyset 分页 |
| | `(schema_id, name)` | btree 部分 | 按 schema 浏览 |
| | `(grade_level)` | btree 部分 | 敏感资产筛选 |
| | `name gin_trgm_ops` | GIN | 表名模糊搜索 |
| `catalog_column` | `(fqn, id)` | UNIQUE 部分 | keyset 分页 + 唯一 |
| | `(datasource_id, fqn, id)` | btree 部分 | 按源筛选 + 分页 |
| | `(table_id, ordinal_position)` | btree 部分 | 表详情字段排序 |
| | `(grade_level)` | btree 部分 | 敏感字段筛选 |
| | `name gin_trgm_ops` | GIN | 字段名模糊搜索 |
| | `(data_type)` | btree | 按类型筛选 |
| | `tags jsonb_path_ops` | GIN | 标签包含查询 |
| `entity_tag` | `(entity_type, entity_id)` | btree | 实体标签查询 |
| | `(tag_key)` | btree | 按标签反查实体 |
| | `(entity_type, entity_id, tag_key)` | UNIQUE 部分 | 防重复打标 |
| `lineage_table_edge` | `(src_fqn)` / `(tgt_fqn)` | btree | 上下游一度查询 |
| `lineage_closure` | `(ancestor_id, depth)` / `(descendant_id, depth)` | btree | 多跳追溯 |
| `change_event` | `(scan_run_id)` / `(severity, detected_at)` / `(entity_type, entity_id)` | btree | 变更查询 |

### 6.2 keyset 分页的索引前提（关键）

行值比较 `(fqn, id) > (:last_fqn, :last_id)` 只有在存在**与排序键顺序一致的复合索引**时才能走 index scan。因此：

- 排序 `(fqn, id)` → 必须建 `(fqn, id)`
- 排序 `(datasource_id, fqn, id)` 且 `datasource_id` 等值 → 必须建 `(datasource_id, fqn, id)`

**索引不匹配即退化为全表排序**，千万行下直接超时。这是 keyset 分页最常见的落地失败点。

### 6.3 为什么 trigram 而非 `tsvector`

元数据检索的主要模式是「子串模糊匹配」（表名/字段名含关键字），`pg_trgm` 的 `gin_trgm_ops` 可直接加速 `ILIKE '%x%'`，且对中文需配合 `lc_collate` 与分词考量。

`tsvector` 适合「分词后的全文检索」，对 `user_order_detail` 这类无空格标识符效果不佳。

**限制**：中文表名/字段名的子串检索需验证 `pg_trgm` 效果，必要时引入分词插件（`pg_bigm` 对中文更友好）。

## 7. 查询范式

### 7.1 keyset 分页（强制）

```sql
-- 首页
SELECT id, fqn, name, table_type, grade_level
FROM catalog_table
WHERE deleted_at IS NULL
ORDER BY fqn, id
LIMIT 20;

-- 后续页：游标来自上一页最后一行
SELECT id, fqn, name, table_type, grade_level
FROM catalog_table
WHERE deleted_at IS NULL
  AND (fqn, id) > (:last_fqn, :last_id)
ORDER BY fqn, id
LIMIT 20;
```

**游标编码**：`cursor = base64(fqn + '|' + id)`，API 返回 `next_cursor`，前端不感知内部结构。

**禁止**：`OFFSET n LIMIT m`（n > 1000）。

### 7.2 带筛选的 keyset

```sql
-- 按数据源 + 分级筛选
SELECT id, fqn, name
FROM catalog_table
WHERE deleted_at IS NULL
  AND datasource_id = :ds_id
  AND grade_level >= :min_grade
  AND (fqn, id) > (:last_fqn, :last_id)
ORDER BY fqn, id
LIMIT 20;
-- 依赖索引 (datasource_id, fqn, id)；grade_level 作为过滤条件回表判断
```

> 注意：若筛选列（如 `grade_level`）也参与排序，则索引须为 `(grade_level, fqn, id)`。**排序键必须与索引前缀一致**，筛选列放前、游标键放后。

### 7.3 模糊搜索（深度受限）

```sql
SELECT id, fqn, name
FROM catalog_table
WHERE deleted_at IS NULL
  AND name ILIKE '%' || :kw || '%'
ORDER BY name, id
LIMIT 1000;          -- 硬上限，超出提示收窄条件
```

**说明**：模糊搜索无法有效 keyset（相关性/匹配顺序无法稳定游标）。业界通行做法是**限制结果深度**（1000 条 / 50 页），超出要求用户收窄条件。若确需深翻，可降级为 `(name, id)` 游标，但需接受 trigram 索引回表开销。

### 7.4 总数问题（keyset 的固有代价）

keyset 分页无法高效提供精确 `COUNT(*)`（千万行 count 需全索引扫描）。

| 场景 | 方案 |
|---|---|
| 列表页「共 N 条」 | 用近似值：`pg_class.reltuples`（误差 <5%，毫秒级） |
| 需精确总数 | 单独 count 查询，加缓存 + 限制触发频率 |
| 搜索场景 | 只返回「是否有下一页」，不给总数 |

**API 契约建议**：返回 `has_more: bool` + `approx_total: number`，而非 `total: number`。

### 7.5 血缘多跳追溯（防环）

```sql
WITH RECURSIVE walk AS (
    SELECT e.tgt_fqn AS node,
           1 AS depth,
           ARRAY[e.src_fqn, e.tgt_fqn] AS path
    FROM lineage_table_edge e
    WHERE e.src_fqn = :start_fqn
  UNION ALL
    SELECT e.tgt_fqn,
           w.depth + 1,
           w.path || e.tgt_fqn
    FROM walk w
    JOIN lineage_table_edge e ON e.src_fqn = w.node
    WHERE w.depth < :max_depth              -- 深度硬上限
      AND NOT (e.tgt_fqn = ANY(w.path))     -- 环检测
)
SELECT DISTINCT node, min(depth) FROM walk GROUP BY node;
```

`NOT (tgt = ANY(path))` 手工防环兼容 PG 11+；PG 14+ 可用 `CYCLE node SET is_cycle USING path`。

**生产建议**：高频追溯走预计算的 `lineage_closure`（`depth` 直接命中），递归仅用于闭包重建兜底。

### 7.6 快照 Diff（签名驱动）

```sql
-- 1) 快速筛出签名变化的表（避免逐字段比对）
SELECT cur.table_id, cur.fqn
FROM catalog_table cur
JOIN table_snapshot prev
  ON prev.table_id = cur.table_id
 AND prev.scan_run_id = :prev_run_id
WHERE cur.datasource_id = :ds_id
  AND cur.deleted_at IS NULL
  AND cur.struct_hash <> prev.struct_hash;

-- 2) 仅对上一步结果展开字段级比对
SELECT c.name, c.struct_hash, s.struct_hash
FROM catalog_column c
LEFT JOIN column_snapshot s
  ON s.column_id = c.id AND s.scan_run_id = :prev_run_id
WHERE c.table_id = ANY(:changed_table_ids)
  AND (s.column_id IS NULL                       -- 新增字段
       OR c.struct_hash <> s.struct_hash);       -- 字段变更
```

删除字段需反向查快照中存在而当前不存在的 `column_id`。

### 7.7 批量 Upsert（写入吞吐）

```sql
INSERT INTO catalog_column (table_id, datasource_id, fqn, name, ...)
VALUES (...), (...), ...          -- 每批 5000–10000 行
ON CONFLICT (fqn) WHERE deleted_at IS NULL
DO UPDATE SET name = EXCLUDED.name, ..., updated_at = now();
```

SQLAlchemy 侧用 `execute_values` / `psycopg2.extras.execute_batch`，**禁止逐条 INSERT**。

> 注意：`ON CONFLICT` 配合部分唯一索引时，冲突目标需写成 `(fqn) WHERE deleted_at IS NULL`。

## 8. 容量复核

| 表 | 行数 | 行大小 | 表+索引 |
|---|---|---|---|
| `catalog_column` | 1500 万 | ~250B | ~8 GB |
| `entity_tag` | 5000 万 | ~80B | ~10 GB |
| `column_snapshot`（保留 6 个月，月 1500 万） | 9000 万 | ~250B | ~45 GB |
| `catalog_table` + `table_profile` | 50 万 | ~3KB | ~3 GB |
| 其余 | — | — | < 2 GB |
| **合计** | | | **~70 GB** |

**主导项是快照**。故保留策略是容量控制的第一杠杆：

| 保留窗口 | 快照容量 |
|---|---|
| 12 个月 | ~90 GB |
| 6 个月 | ~45 GB |
| 3 个月 | ~23 GB |

**建议**：默认保留 6 个月，且快照存储 `snapshot_json` JSONB（压缩后）而非全字段列，可降低 30–50%。若仍过大，考虑快照只存 `struct_hash` + 变更字段（diff-only 存储），全量快照按周期（如每月一次）保留。

## 9. 迁移管理

- 工具：**Alembic**（项目已依赖 SQLAlchemy 2.0）
- 原则：每次模型变更一个 revision，禁止手工改库
- 大表 DDL 须用在线方式：
  - 加列：`ALTER TABLE ... ADD COLUMN`（无默认值时秒级）
  - 加索引：`CREATE INDEX CONCURRENTLY`（不阻塞写入，**注意不能在事务块内执行**）
  - 加约束：先 `NOT VALID` 再加 `VALIDATE`
- 分区表创建与挂载纳入 Alembic 的定时任务（每月预建下月分区）

## 10. 安全设计落点

| 需求 | 落点 |
|---|---|
| 凭据加密 | `datasource_credential.credential_enc BYTEA`（应用层加密，密钥由 KMS/环境变量注入，不入库） |
| 凭据轮换 | `datasource_credential` 支持多版本 + `is_active` 标记 |
| 样本脱敏 | `sample_value.value_masked TEXT`（脱敏后）；原文仅在显式开启时存 `value_enc BYTEA` |
| 样本 TTL | `sample_value.expires_at` + 按月分区整区 drop |
| 审计 | `audit_log` 记录采样、导出、凭据变更、分级人工修正 |
| 人工修正保护 | `entity_tag.source = 'manual'` 的标签，自动引擎不得覆盖 |
