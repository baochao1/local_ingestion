| 项目 | 内容 |
|---|---|
| 模块编号 | MOD-06 |
| 负责需求 | FR-3、FR-7（含 `04` 补充项 FR-7.7 ~ FR-7.9） |
| 优先级 | P0（投入小、客户感知强） |
| 依赖模块 | MOD-02（快照）、MOD-07（影响面）、MOD-10（任务、通知、审计） |
| 被依赖 | MOD-09（变更历史展示） |

---

## 1. 职责与边界

### 1.1 职责

1. **快照比对**：基于 `struct_hash` 与逐字段比对，产出字段级变更
2. **变更分级**：破坏性 / 结构性 / 描述性
3. **变更事件存储**：写 `change_event`（按月分区）
4. **变更订阅与通知**：按粒度订阅，多渠道推送，去重与聚合
5. **变更确认闭环**：责任人确认后关闭

### 1.2 边界（不做）

- 不写快照（属 MOD-02）——只读取比对
- 不做血缘解析（属 MOD-07）——只调用其影响面接口
- 不做分级（属 MOD-05）

## 4. 核心设计

### 4.1 Diff 流程（签名驱动）

```
[触发：扫描任务成功 → MOD-10 编排触发 Diff]
   │
   ├─ 1. 取本次 scan_run_id 与上一次成功的 scan_run_id（基线）
   ├─ 2. 表级快速过滤：比较 table.struct_hash
   │      签名相同 → 跳过（绝大多数表走此路径）
   │      签名不同 → 进入逐字段比对
   ├─ 3. 字段级比对（仅对上一步命中的表）：
   │      ├─ 新增字段（当前有、快照无）
   │      ├─ 删除字段（快照有、当前无）
   │      ├─ 字段变更（struct_hash 不同 → 定位具体属性差异）
   │      └─ 改名（消费 MOD-02 判定结果）
   ├─ 4. 表级增删：当前有快照无 → 新增；快照有当前无 → 删除/孤儿（区分改名）
   ├─ 5. 变更分级 → severity
   ├─ 6. 批量写入 change_event（分区）
   ├─ 7. 匹配订阅 → 聚合去重 → 通知
   └─ 8. 若已接入血缘：调用 MOD-07 计算影响面，补充下游责任人
```

**为什么签名前置过滤关键**：千万字段若逐字段比对，代价不可接受；绝大多数表在两次扫描间不变，签名比对可过滤掉 95%+ 的对象。

### 4.2 变更分级规则（FR-7.2）

| 变更 | severity | 理由 |
|---|---|---|
| 删除表、删除字段 | `breaking` | 下游必然报错 |
| 字段类型收窄（如 `bigint → int`） | `breaking` | 可能溢出/报错 |
| 新增非空约束（无默认值） | `breaking` | 下游写入会失败 |
| 字段类型放宽、新增字段、字段改名 | `structural` | 可能影响下游语义 |
| 描述、标签、负责人变更 | `descriptive` | 不影响运行 |

### 4.3 通知去重与聚合（FR-7.4）

**问题**：一次全库扫描可能产生数万条变更，逐条通知会造成告警风暴。

**方案**：

| 层 | 机制 |
|---|---|
| 聚合 | 按「订阅者 + 数据源 + 变更类型」聚合为一条摘要；破坏性变更可单独推送 |
| 去重 | 同一对象同一变更在冷却期内不重复通知（`notification_log` 判定） |
| 静默 | `notification_subscription` 支持按数据源/库/表静默（FR-7.7） |
| 阈值 | 单次变更量超阈值时只推送摘要 + 前 N 条明细 |

**通道复用现有资产**：`integrations/webhook.py`（含 HMAC 签名）、`notifications.py`（Email/Slack）。

### 4.4 与血缘联动（FR-7.6）

破坏性变更产生后，调用 MOD-07 的影响面接口获取下游表/责任人，将通知范围从「变更对象负责人」扩展到「下游受影响方」。

**依赖**：MOD-07 未上线时此能力降级，仅通知直接责任人（模块需支持该功能不可用时的降级）。

### 4.5 变更确认闭环（FR-7.9）

```
变更事件产生 → 通知责任人 → 责任人确认（已处理 / 误报 / 忽略）
                              └─ 确认后事件关闭，计入变更统计
未确认的破坏性变更 → 超过时限升级通知（FR-7.8）
```

## 7. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 签名前置过滤 + 逐字段展开 | 避免千万字段全量比对 |
| D2 | 只比快照不写快照 | 职责分离；Diff 可独立重跑，换基线灵活 |
| D3 | 变更分级而非平铺 | 破坏性变更必须突出，否则告警失去意义 |
| D4 | 通知聚合去重为默认行为 | 数万条变更逐条推送会直接毁掉用户体验 |
| D5 | 血缘联动支持降级 | MOD-07 排期靠后（P2），不可用时不阻塞本模块主流程 |
| D6 | 消费 MOD-02 的改名判定 | 改名若由本模块自行推断，会与身份稳定逻辑重复且易冲突 |

## 8. 异常与边界处理

| 场景 | 处理 |
|---|---|
| 首次扫描无基线 | 不产生变更事件，仅记录基线 |
| 基线快照已过期被清理 | 回退到可用的最近快照，并标注基线时间 |
| 变更量超阈值 | 推送摘要 + 前 N 条；完整列表走页面查看 |
| 通知发送失败 | 记录 `notification_log`，按退避重试 |
| 血缘不可用 | 降级为仅通知直接责任人，标记影响面未知 |
| 同一对象频繁变更 | 冷却期去重；超频单独标记为「不稳定对象」 |
| 快照缺失（某轮未写） | 跳过该轮，用最近可用基线并告警 |

---

## 9. 验收标准

1. 能列出任意两次扫描间的全部字段级变更
2. 破坏性变更被准确识别（删表/删列/类型收窄/新增非空）
3. 改名被识别为改名，不产生删+增误报
4. 千万字段规模下 Diff 任务可在可接受时间完成（签名过滤生效）
5. 通知按订阅聚合去重，不产生告警风暴
6. 血缘不可用时主流程仍能正常通知（降级验证）
7. 变更可确认、可统计、可导出
