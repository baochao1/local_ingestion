## 一、对标源

### 1.1 开源同类（第一梯队）

| 产品 | 定位 | 作为对标物的价值 |
|---|---|---|
| **OpenMetadata** | 开箱即用的完整协作式元数据平台，连接器生态最丰富 | **资产类型覆盖度**与**开箱体验**的基准 |
| **DataHub**（LinkedIn） | 事件驱动的实时元数据流，aspects 模型 | **元数据变更实时性**与**扩展模型**的基准 |
| **Apache Atlas** | Hadoop 生态治理框架，类型系统 + 标签传播 + Ranger 集成 | **分类分级/标签传播**与**权限联动**的基准 |
| Apache Gravitino | 跨云联邦元数据中心 | 多源联邦场景（本项目暂不涉及） |

### 1.2 商用（决定"天花板"在哪）

| 产品 | 标志性能力 |
|---|---|

| **Collibra** | 强工作流与治理运营（策略、职责、认证） |

### 1.3 标准与标书（评标项 = 需求项）

| 标准/规范 | 关键要求 | 对本项目的意义 |
|---|---|---|
| **GB/T 43697-2024《数据安全技术 数据分类分级规则》**（2024-10-01 实施） | 分级框架为**核心 / 重要 / 一般**三级；规定分类分级的流程、识别与标识 | **投标硬门槛**：分级体系必须能映射/声明到该框架 |
| 行业标准（金融 JR/T 0197-2020 等） | 行业多为 5 级细化，并要求行业数据目录 | 行业项目需提供行业模板 |
| **DCMM**（数据管理能力成熟度，GB/T 36073） | 8 大能力域：数据战略、数据治理、数据架构、数据应用、数据安全、数据质量、数据标准、数据生命周期 | 甲方常以 DCMM 等级（如 3 级）为建设目标，平台需覆盖对应能力域 |
| 《数据安全法》《个人信息保护法》 | 重要数据识别、个人信息保护影响评估、跨境 | 分级结果要能驱动管控（脱敏/权限/审批） |
| 等保 2.0 / 分级保护 | 安全审计、访问控制、身份鉴别 | 审计日志与权限策略是必备项 |

公开的元数据/数据资产目录类采购需求，常见功能项可归纳为 8 条（多份技术文章口径一致）：

1. **元数据采集**：多源自动采集（数据库/数仓/云/IoT）
2. **元数据管理**：分类分级、打标签、自定义注释、版本
3. **数据血缘**：来源—加工—流转的可视化（表级 + 字段级）
4. **数据标准**：业务术语与技术字段的映射
5. **数据发现**：自助检索、过滤、定位
6. **申请/审批**：权限可控的数据访问机制
7. **API 服务**：对外提供元数据服务化能力
8. **资产运营监控**：热度/价值/使用分布

## 二、能力域对标矩阵（标杆侧）

判定分档：**结构性缺失**（整域没建模）/ **半成品**（后端有、界面无，或能触发不能看）/ **深度不足**（有但不够用）/ **已达标**。

| 能力域 | 标杆能力（OpenMetadata / DataHub / Atlas / 商用） | 分档判据 |
|---|---|---|
| **资产对象类型** | OpenMetadata 约 20 类：Table / StoredProcedure / Dashboard / DashboardDataModel / Pipeline / Topic / Metrics / MlModel / Container / SearchIndex / Query / APIEndpoint / DataProduct 等；DataHub 有 Dataset/Chart/Dashboard/DataJob/DataFlow/MLModel | 仅支持 2 类（表/字段）= **结构性缺失**；支持 5 类以下 = **深度不足** |
| **元数据采集** | 数十至上百种连接器；增量采集；调度编排；采集任务可观测 | 仅 1–2 种源 = **结构性缺失**；无增量/无调度 = **深度不足** |
| **血缘** | 表级 + 字段级；SQL 解析；跨系统（ETL/BI）；影响面分析 | 无 = **结构性缺失**；仅表级 = **深度不足** |
| **分类分级** | 分级标准/标签体系 + 自动识别规则 + 人工确认 + 审批；Atlas 有标签传播 | 有规则无界面 = **半成品**；有界面但级别框架不合国标 = **深度不足** |
| **数据质量** | 测试套件（test suite）、规则库、结果趋势、评分、告警 | 无 = **结构性缺失** |
| **数据画像/剖析** | 行/列统计、值分布、空值率、唯一值、采样预览 | 无 = **结构性缺失** |
| **变更追踪** | 结构变更 + 描述性变更检测；订阅与通知 | 有但无影响面 = **深度不足** |
| **权限分析** | 账号/角色盘点、权限矩阵、风险项（越权/闲置） | 无 = **结构性缺失** |
| **检索** | 全文检索 + 多维过滤 + 排序（热度/相关性）+ 高级语法 | 仅关键字 = **深度不足** |
| **业务元数据** | Glossary（术语、层级、负责人）、业务实体、术语—技术字段关联 | 有术语表无关联 = **半成品** |
| **治理协作** | 审批流、工单、任务分派、订阅通知、公告 | 有审批/工单 = **已达标**方向 |
| **系统管理** | 用户/角色/权限策略、认证对接（LDAP/OIDC）、审计 | 无 = **结构性缺失**；有审计无对接 = **深度不足** |
| **资产运营** | 热度、未使用资产、资产 Owner 认领、数据契约 | 无 = **深度不足** |

## 三、标准/标书映射：本项目最容易失分的两处

### 3.1 分级框架与 GB/T 43697-2024 不对齐

国标采用**核心 / 重要 / 一般**三级框架；本项目分级页使用 **L1 内部 / L2 业务敏感 / L3 个人信息 / L4 高敏个人信息 / L5 机密**五级，且概览页另有"L1 公开 / L2 内部 / L3 敏感 / L4 高度敏感"四套命名（见 `.ux-audit/review-report.md` 的 F-006）。

风险：投标应答"是否符合 GB/T 43697"时，既有的 L1–L5 命名**无法直接映射到国标三级**，需要额外解释；两套命名并存更会被质疑一致性。

补缺方向（需产品拍板，见第六节）：在分级字典中增加**国标映射字段**（每个业务级别 → 核心/重要/一般），并在界面上可切换"业务视角 / 国标视角"展示。

### 3.2 DCMM 八域覆盖（甲方常以 DCMM 等级为建设目标）

| DCMM 能力域 | 本项目 | 依据 |
|---|---|---|
| 数据战略 | ❌ | 无规约 |
| 数据治理 | △ | 审批/工单/订阅已有，策略与职责（Owner/认领）无 |
| 数据架构 | ✅ | 四层资产模型（库/schema/表/字段）+ 标准 |
| 数据应用 | ❌ | 无资产运营、无热度（`grep 热度\|popularity` 0 命中） |
| 数据安全 | △ | 分级有；脱敏联动无、权限分析无界面 |
| 数据质量 | ❌ | 规约全（MOD-04 8 端点）、实现零 |
| 数据标准 | △ | 术语表有，无标准落标与技术字段关联 |
| 数据生命周期 | ❌ | 无规约（无归档/销毁策略） |

**结论**：8 域中 1 个达标、3 个部分、4 个空白。若甲方以 **DCMM 3 级**为建设目标，"数据质量"与"数据生命周期"是明确缺项——前者可用既有 `quality/` 引擎低成本补，后者需先补规约。

### 3.3 分级框架缺失国标映射（S0-2 的精确证据）

分级阶梯是**自建 1–5 级**：`platform/classification/queries.py:33-39` 定义 `INTERNAL / SENSITIVE / PII / PII_HIGH / CONFIDENTIAL`，DDL 允许 1–9（`02-schema-ddl.sql:164` `ck_table_grade`、`:206` `ck_column_grade`）。

**代码里没有任何国标映射表或国标编码列**——GB/T 43697-2024 的"核心/重要/一般"三级无法从现有数据推导。补缺只需：加映射字段 + 导出时按国标口径归并（见第五节 S0-2）。

## 八、产品定位漂移警告（应该拒绝的需求）

按"元数据是描述数据是什么、长什么样、谁负责的相对稳定事实"这一判据，以下**不应纳入本产品**：

- **执行计划、慢查询采样、运行时性能**——属 APM 域，进来会带来高频采集、大容量存储、强时效性要求，与元数据的稳定事实模型冲突。
- **脱敏引擎本体**——本项目只做"分级结果驱动脱敏策略"的联动，不做脱敏执行。
- **实时元数据同步**（秒级）——元数据变更以分钟/小时级为准，DataHub 式的事件流架构不是本阶段目标。
