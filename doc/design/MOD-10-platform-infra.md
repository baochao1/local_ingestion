## 4. 核心设计

### 4.1 为什么本模块须与持久化同批（关键）

现有 `APScheduler`（`engine/scheduler.py:78-84`）是**进程内**调度器，已确认单实例部署（Q11），因此不存在多实例重复执行问题。但以下场景仍会造成任务重入：

- 定时任务与手动触发并发
- 上游任务重复触发下游（编排链重放）
- 失败重试与人工重试叠加

后果同样是重复扫描、重复采样、重复告警。

若不在地基阶段统一，各业务模块会各自实现调度与防重，必然重复且不一致，后期收敛成本极高。**因此任务编排是比采样更基础的底座。**

### 4.2 任务模型

```
TaskSpec:  job_type（metadata/sample/profile/classify/lineage/permission）
           scope（datasource_id / 具体对象范围）
           trigger（manual / cron / event）
           policy（retry, timeout, concurrency_key, priority）
TaskRun:   id, status, started_at, finished_at, duration, stats, error
```

生命周期：`pending → running → success / failed / cancelled / timeout`

### 4.3 任务防重（FR-12.3）

> **部署形态已确认（Q11）：单实例部署。**

单实例下不需要分布式锁，采用**进程内锁 + 任务重入保护**即可：

| 机制 | 说明 |
|---|---|
| 重入保护 | 同一 `job_type + scope` 存在 `pending` / `running` 任务时，拒绝重复提交（唯一约束或提交前校验） |
| 进程内锁 | 调度触发与手动触发并发时，以任务状态为准，避免双写 |
| 幂等保证 | 任务重复执行结果一致（NFR-3.4），即便异常重入也不产生重复数据 |

**保留扩展位**：防重逻辑封装为 `LockProvider` 接口。若将来转为多实例部署，替换为 **PostgreSQL advisory lock** 即可，业务代码不变：

```sql
SELECT pg_try_advisory_lock(hashtext('job:' || job_id));
```

不预先引入 Redis / MQ（单实例下无收益，徒增运维组件）。

### 4.4 并发控制（FR-12.4）

| 层级 | 控制 |
|---|---|
| 全局 | 平台级并发上限 |
| 每数据源 | 并发上限（防打爆生产库，与 MOD-03 采样保护联动） |
| 每任务类型 | 如采样并发低于扫描 |

基于 `concurrency_key` 信号量实现；排队任务可见。

### 4.5 任务编排（FR-12.7）

声明式依赖链：

```
扫描成功 → [采样] → [画像, 分级]
扫描成功 → [Diff] → [通知]
血缘/权限采集：独立周期
```

实现：任务完成时发布完成事件 → 编排器按依赖声明触发下游任务。MVP 可用「完成事件 + 规则表」实现，不引入工作流引擎。

### 4.6 重试与退避（FR-12.6）

| 项 | 策略 |
|---|---|
| 可重试错误 | 连接超时、死锁、限流 |
| 不可重试 | 参数错误、权限不足、对象不存在 |
| 退避 | 指数退避 + 抖动，上限次数可配 |

### 4.7 可观测（FR-15.1/15.2）

复用现有资产并扩展：

- `observability/metrics.py`（Prometheus）：扩展任务级指标（成功率、耗时分布、队列长度）
- `observability/health.py`：扩展数据库、调度器、连接器池、分区状态检查
- `observability/alerts.py`：扩展任务失败告警

**链路追踪（NFR-4.4）**：跨模块任务（扫描 → Diff → 通知）以 `scan_run_id` / `trace_id` 串联。

### 4.8 数据保留与分区维护（FR-15.3/15.4）

定时任务：

1. **分区预建**：每月预建下月分区（快照、变更、审计、样本、画像历史）
2. **过期清理**：保留窗口外 `DROP PARTITION`（秒级，禁 `DELETE`）
3. **软删除物理清理**：按批清理 `deleted_at` 过期数据

### 4.9 审计（FR-15.5）

以下动作**必须**留痕：采样、样本预览、导出、凭据变更、人工标注/修正、任务取消、权限变更。

审计由各模块调用本模块统一接口（C10），禁止各模块自行写 `audit_log`。

**无业务依赖**。本模块是底座，被所有模块依赖，不反向依赖任何业务模块——这是保持架构无环的关键。

## 7. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 单实例下用进程内锁 + 重入保护，防重逻辑封装为 `LockProvider` 预留扩展 | 已确认单实例部署（Q11）；不预先引入 Redis/MQ；将来多实例可切 PG advisory lock 而不改业务代码 |
| D2 | 任务编排用「完成事件 + 规则表」，不引入工作流引擎 | MVP 编排需求简单（链式依赖），引入 Airflow 级组件过度 |
| D3 | 编排器不感知业务语义 | 保证无环依赖，业务变化不影响底座 |
| D4 | 审计接口统一，禁止模块自行写表 | 保证审计完整性与格式一致 |
| D5 | 过期数据一律 DROP PARTITION | 千万行 DELETE 不可接受 |
| D6 | 保留现有 Prometheus / Webhook / 通知实现并扩展 | 已有可用资产，不重写 |

## 8. 异常与边界处理

| 场景 | 处理 |
|---|---|
| 实例崩溃导致锁未释放 | PG advisory lock 随连接释放；另设任务超时兜底（超时未心跳视为失败） |
| 任务长时间无进展 | 心跳 + 超时终止 |
| 调度器不可用 | 任务堆积在队列，恢复后按优先级执行 |
| 分区未预建导致写入失败 | 健康检查告警；写入前自动建分区兜底 |
| 通知通道失败 | 记录 `notification_log`，退避重试 |
| 任务依赖的上游失败 | 下游不触发，标记 skipped |

---

## 9. 验收标准

1. 同一定时/手动任务不会被重复执行（重入保护生效）
2. 任务可手动触发、取消、重试
3. 全局与每数据源并发上限生效
4. 扫描 → Diff → 通知 依赖链可自动串联
5. 任务历史、耗时、失败原因可查询
6. 分区自动预建，过期分区被 DROP
7. 采样、导出、凭据变更等关键动作均有审计记录
8. 平台健康端点覆盖数据库、调度器、分区状态
9. OpenAPI 文档完整可用
