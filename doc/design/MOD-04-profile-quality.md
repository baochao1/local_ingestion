## 1. 职责与边界

### 1.1 职责

1. **数据画像**：填充 `table_profile`，产出表与字段的统计特征
2. **质量规则执行**：复用现有 6 类规则引擎执行校验
3. **质量评分与趋势**：表/库级评分，历史趋势
4. **报告导出**：复用 `quality/reporter.py`

### 1.2 边界（不做）

- 不做采样计算本身（由 MOD-03 的 `StatSampler` 提供）
- 不做敏感识别（MOD-05）
- 不修改元数据实体结构（属 MOD-02）

## 3. 数据模型

| 表 | 用途 | 所有权 |
|---|---|---|
| `table_profile` | 当前画像（每表一行 JSONB） | **本模块写** |
| `quality_rule` | 质量规则定义 | **本模块写** |
| `quality_result` | 规则执行结果 | **本模块写** |
| `table_profile_history` | 画像历史（FR-5.7） | **本模块写** |

### 3.1 补充表：`table_profile_history`（FR-5.7）

```sql
CREATE TABLE table_profile_history (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY,
    profiled_date DATE        NOT NULL,
    table_id      BIGINT      NOT NULL,
    datasource_id BIGINT      NOT NULL,
    row_count     BIGINT,
    stats         JSONB       NOT NULL DEFAULT '{}'::jsonb,
    quality_score NUMERIC(5,2),
    profiled_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (id, profiled_date)
) PARTITION BY RANGE (profiled_date);
CREATE INDEX idx_prof_hist_table ON table_profile_history (table_id, profiled_date DESC);
```

> 已同步至 `02-schema-ddl.sql`。理由：`table_profile` 仅存当前值，趋势（FR-5.4/5.7）需要历史序列；按月分区便于保留策略。

## 4. 核心设计

### 4.1 画像流程

```
[任务触发：定时 / 手动 / 扫描完成后编排]
   │
   ├─ 1. 取待画像表列表（按数据源策略：全部 / 白名单 / 变更过的表）
   ├─ 2. 大表判定（FR-5.8）：估算行数超阈值 → 走采样率画像或跳过
   ├─ 3. 调用 MOD-03 C3：StatSampler.sample_stats(table_id, columns)
   │      返回 per-column 统计（null_count / distinct_count / min / max / mean / stddev）
   ├─ 4. 组装 stats JSONB（每表一行，见数据模型设计决策 D）
   ├─ 5. 写入 table_profile（upsert）+ table_profile_history（append）
   ├─ 6. 执行质量规则（对配置了规则的表/字段）
   ├─ 7. 计算质量评分 → 写入 quality_result 与 history
   └─ 8. 更新任务状态（MOD-10）
```

### 4.2 每表一行 JSONB 结构

```jsonc
{
  "col_name": {
    "null_count": 12,
    "null_ratio": 0.0012,
    "distinct_count": 8934,
    "min": "2020-01-01",
    "max": "2026-09-30",
    "mean": 123.45,          // 数值型
    "stddev": 45.6,          // 数值型
    "top_values": ["A", "B"] // 低频基数时记录
  }
}
```

设计依据：`TableProfile` 的 `minValue/maxValue/mean/sum/stdDev` 本就是 `Dict[str, Any]`（`schema/data/table.py:36-40`），天然是 per-column 语义。此举把画像表从「千万行」降到「数十万行」。

### 4.3 质量规则执行

**复用现有资产**：

- `quality/rules.py`：6 类规则（not_null / unique / range_check / pattern_match / referential / custom_sql）
- `quality/rules.py:582 RuleFactory.from_json_schema`：可从 JSON Schema 自动生成规则，作为冷启动手段
- `quality/validator.py`：TableValidator / ColumnValidator / BatchValidator
- `quality/reporter.py`：HTML/JSON 报告

**规则来源三类**：

1. 系统内置（非空、主键唯一等结构推导）
2. 用户自定义（`quality_rule` 表配置）
3. 由 JSON Schema 自动推导（`RuleFactory`）

### 4.4 质量评分

| 项 | 方案 |
|---|---|
| 表级评分 | 该表所有规则通过率的加权平均，权重取 `quality_rule.severity`（error > warning > info） |
| 库/源级评分 | 下级表评分的加权平均（可按表重要度/行数加权） |
| 趋势 | 每次评分写入 `table_profile_history.quality_score`，形成时间序列 |
| 新鲜度 | `profiled_at` 超过有效期（可配，默认 7 天）标记过期，UI 提示重算 |

### 4.5 大表策略（FR-5.8）

| 表规模 | 策略 |
|---|---|
| < 阈值 A（如 1000 万行） | 全量聚合下推 |
| 阈值 A ~ B | 采样率画像（`TABLESAMPLE`），标注 `sample_rate` |
| > 阈值 B 或分区表 | 跳过或仅画像最新分区（可配） |

所有画像均**不下拉行数据**，聚合在数据库侧完成。

## 7. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 每表一行 JSONB 存画像 | 千万列降到数十万行；`TableProfile` 模型本就是 per-column 字典 |
| D2 | 统计计算完全下推 | 拉行到平台计算既慢又有采样偏差（FR-5.2） |
| D3 | 复用现有规则引擎而非重写 | `quality/rules.py` + `validator.py` + `reporter.py` 已可用 |
| D4 | 历史独立表 + 分区 | 趋势需要时间序列；当前值表保持精简 |
| D5 | 画像任务独立调度 | 避免拖慢元数据扫描（FR-5.6） |
| D6 | 大表分级策略 | 无差别全量聚合会拖垮生产库 |

---

## 8. 异常与边界处理

| 场景 | 处理 |
|---|---|
| 大表聚合超时 | 降级为采样率画像；仍超时则跳过并记录 |
| 字段类型不支持聚合（如 BLOB） | 跳过统计，标记原因 |
| 规则执行 SQL 失败 | 记录失败，不影响其他规则 |
| 表被删除 | 画像标记失效，随保留策略清理 |
| 画像结果为空表 | 正常记录 row_count=0，不视为失败 |
| 数据源不可达 | 任务失败，按 MOD-10 重试策略 |

---

## 9. 验收标准

1. `TableProfile` 空壳被填实，主要表的画像数据完整
2. 画像过程中平台不拉取业务表全量数据
3. 超大表按策略降级，不产生生产库长查询
4. 质量规则可执行并产出通过率与评分
5. 评分趋势可查询（历史序列完整）
6. 画像过期可被识别并提示重算
7. 报告可导出（HTML/JSON）
