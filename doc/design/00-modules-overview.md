## 1. 模块划分原则

1. **按业务能力域划分**，而非按技术分层。每个模块对一组完整的用户需求负责。
2. **单一数据所有权**：每张表只有一个写者（Owner），其他模块只读。避免多模块并发写同一张表导致的覆盖与不一致。
3. **横切能力下沉**：调度、可观测、审计、认证等公共能力统一由平台基础模块提供，业务模块不各自实现。
4. **模块间优先通过共享表 + 任务编排解耦**，减少直接调用，避免循环依赖。

## 4. 数据所有权矩阵（关键契约）

**规则：每行只有一个 Owner（写者），其余为只读。跨模块写入必须通过 Owner 模块提供的接口，禁止直接写表。**

| 表 | Owner（写） | 只读方 |
|---|---|---|
| `datasource`、`datasource_credential` | MOD-01 | MOD-02、03、06、09、10 |
| `catalog_database` / `catalog_schema` | MOD-02 | 全部 |
| `catalog_table` / `catalog_column` | MOD-02（主记录） | 全部 |
| ↳ `grade_level` / `grade_code` 列 | **MOD-05**（仅更新此列） | MOD-09、11 |
| ↳ `tags`、`columns_json` 列 | MOD-02（结构） + MOD-05/MOD-09（标签） | — |
| `entity_tag` | **MOD-05**（`security` 命名空间）<br>**MOD-09**（`business` 命名空间） | MOD-08、11 |
| `table_profile` | MOD-04 | MOD-05、09 |
| `quality_rule` / `quality_result` | MOD-04 | MOD-09 |
| `sample_value` | MOD-03 | MOD-05（内存消费为主） |
| `scan_run` | MOD-10（创建/状态流转） | 全部 |
| `table_snapshot` / `column_snapshot` | MOD-02（写入） | MOD-06（比对读取） |
| `change_event` | MOD-06 | MOD-07（影响面）、09、10 |
| `lineage_table_edge` / `lineage_column_edge` / `lineage_closure` | MOD-07 | MOD-06、09 |
| `account` / `account_grant` | MOD-08 | MOD-09、11 |
| `classification_tag` / `classification_rule` | MOD-05 | MOD-09 |
| `notification_subscription` / `notification_log` | MOD-06 | MOD-10 |
| `approval_request` | MOD-12 | MOD-09、11 |
| `governance_ticket` / `governance_comment` | MOD-12 | MOD-06（联动）、10 |
| `audit_log` | MOD-10 | MOD-11、12 |

### 4.1 两个必须遵守的写入约束

**约束 A：`entity_tag` 命名空间隔离**

`entity_tag` 有两个写者（安全标签 vs 业务标签），必须靠命名空间隔离，否则会互相覆盖：

| 命名空间 | Owner | 含义 |
|---|---|---|
| `security.*` | MOD-05 | 分类分级标签（`PII_PHONE`、`L3_SENSITIVE`…） |
| `business.*` | MOD-09 | 业务标签/术语（`术语:订单`、`域:交易`…） |

实现上以 `tag_key` 前缀区分，各模块只允许写入与清理自己命名空间的行。

**约束 B：`catalog_column` 的字段级写入隔离**

MOD-02 写主记录（结构信息），MOD-05 只回写 `grade_level` / `grade_code` 两列。任何模块不得在更新自己负责列时覆盖他人列——批量 `UPDATE` 必须限定列名，禁止整行 `model_dump()` 覆盖写。

> 这条是现有代码最容易踩的坑：现在 `Table` / `Column` 是整体 Pydantic 模型，落库时若直接整体覆盖，会抹掉其他模块写入的分级结果。

## 5. 模块间交互模式

按耦合度从低到高，共三种：

### L1 共享数据表 + 状态（首选，异步解耦）

模块 A 写表，模块 B 读取。通过 `scan_run.status` 或实体状态字段驱动。

**示例**：MOD-02 扫描完成写入快照并置 `scan_run.status='success'` → MOD-06 检测到后执行 Diff。

**优点**：无调用耦合，可独立部署与重试。
**适用**：绝大多数跨模块协作。

### L2 模块内服务接口（同步调用）

同进程内直接调用 Python 接口，用于需要即时返回结果的场景。

**示例**：MOD-04 调用 MOD-03 的 `StatSampler.sample_stats(table)`；MOD-05 调用 MOD-03 的 `ValueSampler.sample_values(column)`。

**约束**：只允许**单向**依赖，禁止形成环。

### L3 任务编排（由 MOD-10 统一驱动）

需要串行/并行编排时，由 MOD-10 的任务编排能力串联，而非模块间互相调用。

**示例**：扫描完成 → 触发 Diff → 触发通知，由 MOD-10 定义依赖链。

### 5.1 循环依赖的解法（重要）

**MOD-03（采样）与 MOD-05（分级）存在天然双向需求**：

- MOD-05 需要 MOD-03 的样本值做回验
- MOD-05 判定高敏后要求 MOD-03 停止采样并清除样本

若直接互相调用即成环。**解法**：

```
MOD-05 ──写──▶ entity_tag / catalog_column.grade_level   （表）
MOD-03 ──读──▶ catalog_column.grade_level                （表，采样前检查熔断）
```

即：MOD-03 采样前**读表**判断该列是否已判定为高敏，而非调用 MOD-05 接口；MOD-05 需要清除样本时，通过 **MOD-10 下发异步任务**给 MOD-03。如此双向需求全部降级为单向依赖。

**同理**：MOD-02 与 MOD-05 之间，MOD-05 只回写 grade 列，MOD-02 不感知 MOD-05 存在。

## 9. 统一约定（各模块详细设计须遵守）

1. **分页**：所有列表接口一律 keyset 游标分页（设计文档 §7）
2. **软删除**：业务实体一律 `deleted_at`，禁止物理硬删（千万级级联风险）
3. **批量写**：一律 `execute_values` + `ON CONFLICT`，禁逐条 INSERT
4. **任务化**：耗时操作一律走 MOD-10 任务编排，禁止在 HTTP 请求内同步执行
5. **审计**：采样、导出、凭据变更、人工标注一律调用 MOD-10 留痕
6. **凭据**：任何模块不得自行解密持久化凭据，一律经 MOD-01 的 C1 接口获取连接
7. **幂等**：所有任务可重复执行且结果一致（NFR-3.4）
