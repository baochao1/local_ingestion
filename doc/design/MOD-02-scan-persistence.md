## 1. 职责与边界

### 1.1 职责

1. **方言抽象**：统一各数据库的系统表查询与类型映射
2. **元数据采集**：库 / schema / 表 / 字段的抽取（全量与增量）
3. **持久化**：`PostgresSink` 批量落库，维护 `catalog_*` 实体
4. **快照写入**：每轮扫描写入 `table_snapshot` / `column_snapshot`
5. **实体身份稳定**：稳定 ID、改名检测、孤儿处理（FR-13）
6. **结构签名**：`struct_hash` 计算与变更前置判定

### 1.2 边界（不做）

- 不做数据采样（MOD-03）
- 不做版本 Diff（MOD-06）——只负责写快照
- 不做血缘解析（MOD-07）
- 不做任何分级/画像/质量判定

CREATE TABLE entity_alias (

## 4. 核心设计

### 4.1 方言抽象层（FR-2.4）

**现状问题**：类型映射与系统表查询在各连接器内重复实现且硬编码（`postgres.py:329-393`），新增数据源需复制粘贴全部逻辑。

**抽象设计**：

```python
class Dialect(ABC):
    # 元数据查询
    def list_databases_sql(self) -> str
    def list_schemas_sql(self) -> str
    def list_tables_sql(self) -> str
    def list_columns_sql(self) -> str

    # 类型归一化
    def normalize_type(self, raw_type: str, **meta) -> str

    # 能力声明
    @property
    def supports_sampling(self) -> bool
    def sample_sql(self, table: str, rate: float) -> str   # 见 MOD-03

    # 权限/账号查询（供 MOD-08）
    def list_accounts_sql(self) -> str
    def list_grants_sql(self) -> str
```

各数据库实现一份 `Dialect`，连接器只负责连接与执行，不再内含 SQL 与映射逻辑。

### 4.2 扫描流程

```
[任务触发：手动 / 定时 / 事件]
   │
   ├─ 1. MOD-01 获取连接（purpose=scan）+ 扫描策略
   ├─ 2. 预检（FR-2.9）：统计待扫库/schema/表数量，超阈值告警
   ├─ 3. 递归抽取（database → schema → table → column）
   │      每完成一批写 checkpoint（可中断续跑）
   ├─ 4. 计算 struct_hash（表级 + 字段级）
   ├─ 5. 身份解析：
   │      ├─ 按 FQN 匹配已存在实体 → 更新
   │      ├─ 未匹配 → 尝试改名检测（FR-13.2/13.3）→ 命中则更新 ID 保持、记 alias
   │      └─ 仍未匹配 → 新增实体
   ├─ 6. 批量 upsert 到 catalog_*（execute_values + ON CONFLICT）
   ├─ 7. 写快照 table_snapshot / column_snapshot（分区）
   ├─ 8. 孤儿检测：本轮未出现且未删除的实体 → 标记 orphan 待确认（FR-13.5）
   └─ 9. 更新 scan_run 状态 → MOD-10 触发下游任务（Diff）
```

### 4.3 批量写入策略

| 项 | 方案 |
|---|---|
| 写入方式 | `execute_values` + `INSERT ... ON CONFLICT (fqn) WHERE deleted_at IS NULL DO UPDATE` |
| 批次 | 5000–10000 行/批 |
| 冲突目标 | 部分唯一索引需写成 `ON CONFLICT (fqn) WHERE deleted_at IS NULL` |
| 列更新范围 | **只更新本模块负责列**，禁止整行覆盖（保护 MOD-05 写入的 grade，见总览约束 B） |
| `columns_json` | 同事务内随 `catalog_column` 一并写入；提供按 `table_id` 重建任务 |

### 4.4 实体身份稳定（FR-13）

**问题**：以 `fqn` 为标识，改名会被判为「删 + 增」，导致血缘断裂、标签丢失、Diff 误报。

**方案**：

| 层 | 策略 |
|---|---|
| 稳定标识 | 内部 `id` 为唯一稳定标识，`fqn` 仅为当前名称（可查属性） |
| 表改名检测 | 同 schema 内，未匹配的新表与候选删除表做**字段集合重合度**比对：<br>重合度 ≥ 阈值（建议 0.8）且表名相似度达标 → 判定改名 |
| 字段改名检测 | 同表内，类型相同 + 位置相邻 + 名称相似度达标 → 判定改名 |
| 置信度分级 | 高置信自动采纳；中低置信标记 `pending_confirm`，由人工确认或驳回 |
| 历史名留存 | 改名后旧 FQN 写入 `entity_alias`，支持按曾用名检索 |
| 血缘兼容 | 血缘边以 `entity_id` 为主、`fqn` 为辅；改名后 `entity_id` 不变，血缘自动保持 |

**孤儿处理（FR-13.5）**：源端已不存在的实体不立即删除，标记 `orphan` 待确认。保留其历史、标签与血缘；人工确认后软删，或源端恢复后自动复活（按 ID 匹配）。

### 4.5 结构签名 `struct_hash`

定义见数据模型设计决策 E。作用：

- 增量扫描：签名未变则跳过后续处理
- 供 MOD-06 做 Diff 前置过滤（只比对签名变化的表）
- 改名检测的输入之一（字段集合特征）

## 7. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 建立 `Dialect` 抽象层 | 消除各连接器重复 SQL 与硬编码类型映射，新增数据源成本从「复制粘贴」降为「实现一个 Dialect」 |
| D2 | 稳定 ID + `entity_alias` 而非以 FQN 为身份 | 改名场景下保持血缘、标签、历史不丢失（FR-13） |
| D3 | 孤儿标记而非立即删除 | 源端临时不可见（权限变更、网络抖动）不应导致元数据与血缘被销毁 |
| D4 | 只写快照不做 Diff | 职责分离；Diff 由 MOD-06 独立执行，可重跑 |
| D5 | 保留现有 checkpoint 机制 | 已有实现（`pipeline/base.py:182-193`），仅需把状态存储迁至 PG |
| D6 | 批量 upsert 且限定更新列 | 性能 + 保护其他模块写入的列（总览约束 B） |

### 7.1 实施前必须修复的现有缺陷

1. **`cli/commands/scan.py:142` 导入错误**：导入 `PostgreSQLSourceConnector`，实际类名为 `PostgresSourceConnector`（`postgres.py:25`），`scan postgres` 必然 ImportError。
2. **`DatabasePipeline` 无 transform 钩子**：`database_pipeline.py:261,391,405` 直接调用 `sink.write_table`，绕过了 `TablePipeline.transform`（`:211,257`）。两条路径行为不一致，后续任何处理逻辑会被静默绕过。**须补齐钩子后再扩展处理逻辑。**
3. **`SinkConnector` 需泛化**：`connect()` 签名硬编码 `FileSinkConfig`（`base.py:121`），`BaseFileSink` 含 `_file_handle`（`file_sink.py:62`），实现 `PostgresSink` 前须解耦。
4. **状态存储迁移**：`FileStateStore`（`engine/state.py:160-217`）写文件，多实例下不可用，须迁至 PG。

## 8. 异常与边界处理

| 场景 | 处理 |
|---|---|
| 单个库/表抽取失败 | 记录失败明细，继续其余对象；整体标记部分成功 |
| 连接中断 | checkpoint 已持久化，重启后续跑 |
| 超大库（表数超阈值） | 预检阶段告警；按 schema 分片执行 |
| 权限不足无法读某 schema | 跳过并记录，不中断整体 |
| 改名检测误判 | 中低置信标记待人工确认，不自动采纳 |
| 同名不同库 | FQN 全局唯一，按数据源隔离 |
| 任务被取消 | 检测取消信号，在批次边界安全退出 |

## 9. 验收标准

1. 千万级字段全量扫描可在分钟级完成落库（批量 upsert 生效）
2. 扫描中断后可从 checkpoint 续跑，不重复全量
3. 增量扫描只处理 `struct_hash` 变化的对象
4. 表改名被识别为改名而非删+增，血缘与标签保持
5. 孤儿实体被标记而非删除，支持确认与恢复
6. `scan postgres` 命令可正常执行（缺陷 1 已修复）
7. 多实例部署下同一扫描任务不重复执行（依赖 MOD-10）
8. 扫描不覆盖 MOD-05 写入的 `grade_level` 列
