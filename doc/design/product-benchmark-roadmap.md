## 一、产品定位：现在 vs 应该是

| | 现在实际是 | 应该是什么 |
|---|---|---|
| **一句话** | 一个**表结构登记簿 + 变更告警器** | 一个**可浏览、可治理、可审计的元数据资产平台** |
| **主入口** | 一个搜索框（必须先知道表名） | **层级浏览**（库→schema→表→字段）+ 全局搜索 |
| **资产范围** | 表、字段（视图混装） | 库、schema、表、视图、字段、**索引、约束**、存储过程 |
| **治理深度** | 扫描 → 分级（**跑完即结束**） | 扫描 → 分级 → **复核 → 审批 → 发布 → 驱动下游策略** |
| **服务对象** | DBA 的最浅层需求（纳管 + 看变更） | 四类角色（DBA / 治理合规 / 分析业务 / 安全审计） |

**核心矛盾**：产品的能力集中在"**把元数据取进来**"（摄取），而"**在元数据上做判断和治理**"（治理）这一半基本是空的。PRD §1.2 自己就写了这个判断——"摄取是一次性动作，治理是持续性状态"——但实现停在了摄取侧。

## 二、对标矩阵

### 2.1 资产对象类型（对标 `benchmark-metadata-platform.md` §1）

| 对象 | 标杆 | 本产品 | 判定 |
|---|---|---|---|
| Database / Schema | ✅ | 模型 ✅ 采集 ✅ **接口 ❌ 界面 ❌** | **半成品**（数据在库里躺着） |
| Table / Column | ✅ | ✅ 全链路 | 已达标 |
| View / MaterializedView | ✅ 独立可筛 | 采集时混入 Table，检索无此类型 | **深度不足** |
| **Index** | ✅ | ❌ 全链路零 | **结构性缺失** |
| **Constraint（PK/FK/Unique/Check）** | ✅ | ❌ 全链路零 | **结构性缺失** |
| StoredProcedure / Function | ✅ | ❌ | 结构性缺失 |
| Trigger / Sequence / Partition（作为资产） | ✅ | ❌（分区只有运维视图） | 结构性缺失 |
| 消息/BI/ML/文件/API 资产 | ✅ | ❌ | **建议不做**（见 §五） |

### 2.2 分类分级七段式（对标 `benchmark-classification.md` §2）

**这是本次对标最关键的发现：底层能力比预期好，但工作流断了四段。**

| 段 | 环节 | 标杆要求 | 本产品现状 | 判定 |
|---|---|---|---|---|
| ① | 资产梳理 | 必须 | ✅ 扫描器采库/schema/表/字段 | 达标 |
| ② | 规则配置 | 必须，且**标准可配 + 行业模板** | ⚠️ `rules.py` 内置词典/正则/类型启发式；`classification_rule` 表存在但**无管理界面**；分级标准无法自定义 | **半成品 + 深度不足** |
| ③ | **自动识别** | 必须 | ✅ **达标，且是亮点**——`scan/service.py:170,184,289` 扫描后自动跑分级（`classify=True`），新入库行直接带 `grade_level` 与 PII 标记 | **达标** ✨ |
| ④ | 人工复核 | 必须，支持批量 | ❌ 设计有 FR-9.5"人工修正优先"（`source='manual'` 不被覆盖），但**无界面可操作** | **半成品** |
| ⑤ | **审批发布** | 必须，按级别分级审批 | ❌ **MOD-05 设计里就没有这一环**；而 `approval_request` 表已定义 `classification`/`sensitive_tag` 资源类型与 `classify`/`sensitive_tag` 动作——**零调用** | **结构性缺失 + 能力闲置** |
| ⑥ | 结果管理 | 必须，含覆盖率/清单导出 | ❌ MOD-05 四页全为降级占位；分级结果**唯一出口**是搜索的 `gradeMin` 筛选（`search/repository.py:108,140`） | **半成品** |
| ⑦ | 变更联动 | 必须，驱动脱敏/权限/告警 | ❌ 分级结果不驱动任何下游策略 | **结构性缺失** |

**两个必须点出的判断：**

**判断一：③ 是达标的，且比多数自研产品好。** "扫描后自动分级、新字段自动获得级别"这一点做到了——对标里"新增字段不自动识别（退化为一次性项目）"这个常见缺陷，本项目**没有**。这个能力要保住，不要推翻重做。

**判断二：⑤ 不是"没做审批"，而是"审批做好了没接进来"。** `approval_request` 表（`02-schema-ddl.sql:741-762`）明确预留了分类分级场景：

```sql
resource_type TEXT NOT NULL,   -- asset / classification / sensitive_tag / datasource
action_type   TEXT NOT NULL,   -- publish / classify / sensitive_tag / delete
```

MOD-12 的审批界面已经能用（详情/通过/驳回，带 `ConfirmDanger`）。**MC-05 只要在分级结果提交时创建一条 `approval_request`，审批通过后回写 `entity_tag` 即可。** 这是**接线**，不是新建模块——修复成本远低于它看起来的样子。

**判断三：整个⑥⑦缺失导致分级结果没有任何业务价值出口。** 分级算出来了，写进了 `grade_level`，然后……只能用来筛选。**不驱动脱敏、不驱动权限、不驱动告警、也没有报表。** 对标基准的原话是"分级结果不驱动下游策略 = 精美报表"——本产品连报表都还没有。

## 三、产品形态建议（功能蓝图）

### 3.1 资产模型（建议最终形态）

```
Datasource（数据源）
 └─ Database（库）              ← 补接口+界面（P0）
     └─ Schema                 ← 补接口+界面（P0）
         └─ Table / View       ← View 独立类型、可筛（P1）
             ├─ Column         ← 已有
             ├─ Index          ← 补采集+模型+变更（P2）
             └─ Constraint     ← 补采集+模型+变更（P2）
         └─ StoredProcedure    ← 补采集（P2，血缘需要）
```

**分级/标签/owner/描述** 可挂在 Database / Schema / Table / Column 四层（当前只有后两层有 `grade_level`，库和 schema 有 `owner`/`tags` 字段但无分级——建议明确：**库/schema 作为导航容器，不做分级**，避免分级管理复杂度翻倍）。

### 3.2 主入口：层级浏览（补 P0）

左树右表：左侧 `数据源 → 库 → schema` 树，右侧该层级下的表列表，点击进表详情。
**与搜索并列，而非替代。** 这是"让用户发现自己有什么数据"的唯一实现方式。

### 3.3 治理闭环（补 P1）

```
扫描 ──→ 自动分级（已有）──→ 复核工作台 ──→ 审批 ──→ 发布生效 ──→ 驱动策略
        ③               ④            ⑤        ⑥          ⑦
    已有，保住        待建          接线即可   待建        待建
   ────────────────────────────────────────────────────────────────
   反模式警示：④⑤⑥⑦ 全缺 → "自动分级直接生效" → 误报直接进生产策略
              （一个电话号码被误判为敏感 → 脱敏导致业务故障）
```

**审核流程的设计要点**（对标 `benchmark-classification.md` §4）：
- **按级别分级审批**：L1–L2 免审直接生效，L3+ 需审批——**一刀切全审批会让队列爆炸，实际沦为批量点"通过"**
- 复核工作台必须支持**批量确认/批量修正**（一张表 200 个字段，逐个点会崩溃）
- 审批与结果**必须打通**（审批完自动生效，不要手工再改一遍）
- 分级变更留痕可回溯（"三个月前这个字段是几级"）

**P1-1/2/3 实施记录（2026-10-05）**

- 后端新增 `platform/classification/queries.py`（覆盖率 / 敏感资产清单 / 标准 / 规则）、
  `annotation.py`（人工标注 + 审批载荷）、`api/routers/classification.py`（9 个接口中的 7 个）。
- 前端新增 4 个页面与 `api/classification.ts`，`/app/classification/*` 四个路由不再降级。
- **顺带修复两处既有缺陷**：
  1. `GradeTag` 只认 L1–L4，而引擎会判到 **L5（机密）**——L5 数据被渲染成「未分级」，
     概览的分级分布因此显示错误。已扩到 5 级。
  2. `camelize()` 不认识 dataclass，导致任何传给 `KeysetPage` 的 dataclass 都会把 snake_case
     漏给前端。已在公共组件里补齐（与 BaseModel 分支对称）。
- **暴露出的规则质量问题（待处理）**：`rules.py` 的 `_PERSON_NAME` 正则把所有可选前缀设为
  可选，导致裸 `name` 一律命中 L3——`catalog_table.name`、`tenant.name` 这类**表名/库名字段
  被误判为个人信息**；`ip` 同理。分区表（`audit_log_202501`…）未归并，敏感清单被分区刷屏。
  复核工作台现在可以逐条修正，但规则本身需要收紧。


### P2 — 结构性扩展（需采集器 + 模型 + 变更检测协同）

| # | 事项 | 说明 |
|---|---|---|
| P2-1 | **索引采集与建模**（`pg_index`） | 业务价值最高的缺失项——删索引是性能事故首因，当前完全失明 |
| P2-2 | 约束采集（`pg_constraint`：PK/FK/Unique/Check） | 表结构的基本信息 |
| P2-3 | 变更类型扩展（索引/约束/视图定义/schema 级） | 同时**放开 `ck_change_type` 硬编码枚举**，改为可扩展 |
| P2-4 | 存储过程采集（`pg_proc`） | 血缘完整性依赖 |
| P2-5 | 覆盖率统计与合规清单导出 | 标书必考项 |

### P3 — 打磨

## 五、明确不做的（避免产品定位漂移）

| 需求 | 判断 | 理由 |
|---|---|---|
| **执行计划采集** | ❌ 不做 | 运行时性能诊断数据，归属 APM/慢查询分析（pg_stat_statements、pgBadger）。元数据按天变，执行计划按毫秒变 |
| 消息/BI/ML/文件/API 等非关系型资产 | ❌ 本期不做 | 目标用户是 DBA 与治理人员，数据源类型为关系库。扩到 20 种资产类型是另一个产品 |
| 数据脱敏执行 | ⚠️ 只做联动，不做引擎 | 分级结果可**驱动**脱敏策略，但脱敏引擎本身通常由数据安全产品承担 |
| 实时元数据同步 | ❌ 不做 | 与"按天扫描"的定位冲突 |

**过滤器**：这个能力服务的用户任务，在本产品的目标场景里真实存在吗？

## 六、需要拍板的产品决策

| # | 决策 | 选项 | 建议 |
|---|---|---|---|
| 1 | **审批的适用范围** | (A) 全部级别都审批 (B) **仅 L3+ 审批** (C) 不审批，只留痕 | **B**——A 会让队列爆炸并沦为形式，C 合规站不住 |
| 2 | **资产类型扩展档位** | (A) 仅索引+约束 (B) 再加视图独立+存储过程 (C) 完整对象模型 | **分两步走 A → B**，按业务价值排序 |
| 3 | **库/schema 是否作为可治理对象** | (A) 一等资产（可分级/可变更追踪） (B) **仅导航容器** | **B**——成本低且符合认知；A 会让分级管理复杂度翻倍 |
| 4 | **MOD-08 权限分析 / MOD-11 RBAC 是否本期做** | — | 建议**延后**：系统当前**没有任何认证**，在"谁能看什么"未定的前提下投入权限分析收益有限 |
