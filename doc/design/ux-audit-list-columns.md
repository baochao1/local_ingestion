# 全站列表页 信息架构审计（列结构专项）

> **第二轮审计**。方法论相较上一轮有三处补强（skill 变更已落到 `~/.claude/skills/ux-page-audit/`）：
> 1. 新增**强制的信息架构环节**——"核心任务 → 需要的信息 → 页面现状"三列表，在任何点击之前做；
> 2. 新增**规约 diff**——把 FE-01 定义的列与实际实现的列双向对比（规约有实现无 = 缺失；实现有规约无 = 多余）；
> 3. 报告模板新增「信息架构评估」独立章节，并**强制信息架构类发现进统一编号清单+定级**。
>
> 触发原因：上一轮的列结构发现（`ux-audit-full.md:170-171`）写在了「逐页细化分析」的 bullet 里，
> 没编号、没定级、没进实施顺序——等于没提。这一轮把它补上，并扫全站。
>
> 范围：8 个列表页。证据：FE-01 规约段落 + 页面实现代码 + 后端接口返回结构。
> 目标用户：DBA / 数据治理人员。核心关注：**该不该动它**、问题出在哪、谁负责、急不急。

---

## 总体结论

8 个列表页里，**6 个的第一列是规约中根本不存在的裸 ID 列**，且在其中 2 页它是**唯一的详情入口**。

更严重的是：**决定"该不该动它"的那类字段——环境、负责人、健康、优先级、SLA、进度——在 8 个页面里集体缺席**。其中数据源的**连接地址、环境、分组、负责人**在**全系统任何界面都看不到**（列表没有，详情页也没有），而后端 `_to_view()` 早已返回这些字段。

**这不是数据缺失，是界面在丢弃数据。** 后端 `list_datasources` 已经在支持 `environment` / `group_name` 筛选参数，前端筛选栏一个都没暴露。

因此本轮结论：**列结构问题是全站性的，不是数据源一页的个例**；但修复成本极低——**数据源列表的完整改造可做到零后端改动**。

## 一、横切发现（整体变更，一次改完全站受益）

### H1　裸 ID 列占据了 6/8 页的首列，而规约里没有它

| 页面 | 首列 | FE-01 规约里有 ID 吗 | 规约要求的首列 |
|---|---|---|---|
| 数据源 `/datasources` | `ID` | ❌ 没有 | 名称 |
| 变更 `/changes` | `ID` | ❌ 没有 | 时间 |
| 订阅 `/subscriptions` | `ID` | ❌ 没有 | 订阅者 |
| 术语 `/business/terms` | `ID` | ❌ 没有 | 术语编码 |
| 审批 `/governance/approvals` | `ID` | ❌ 没有 | 标题 |
| 工单 `/governance/tickets` | `ID` | ❌ 没有 | 标题 |
| 任务 `/tasks` | `任务ID` | ✅ **有** | 任务ID |
| 审计 `/tasks/audit` | `时间` | ✅ 无 ID | 时间 |

**6 个页面的 ID 列都是实现阶段自行加的，规约里一个都没有。** 这不是设计决策，是列表模板复制粘贴的产物——而任务列表用了 `任务ID`（规约本来就有）恰好说明：**不是所有 ID 都该删**（见 H3）。

### H2　ID 列同时是唯一的详情入口

```tsx
// DataSourceListPage.tsx:55 —— 名称是纯文本，点不动
render: (id: number) => <Link to={`/app/datasources/${id}`}>{id}</Link>
// ChangeListPage.tsx:35 —— 同样
render: (id: number) => <Link to={`/app/changes/${id}`}>{id}</Link>
```

用户被迫在"看不懂的数字"上寻找可点元素来进入详情，而**他认得出的那一列（名称 / 标题 / FQN）是死的**。上一轮审计对数据源页写过"「编码」是纯文本，不可点（详情入口只有 ID 列）"，但没推广到其它页，也没进清单。

### H3　"标识列"要分开判断，不要一刀切

| 类型 | 例子 | 判定 | 理由 |
|---|---|---|---|
| 代理主键 | 数据源 `3`、变更 `17` | **删** | 用户无法心算、从不引用；详情入口改挂名称列 |
| 业务标识符 | 任务 `#123`、术语编码 `TERM_001`、FQN | **留** | 用户在沟通、检索、排障时会引用（"3 号任务挂了"） |
| 内部编码 | 数据源 `code`（`ds_pg_01`） | **降级** | 只在系统内唯一，用户不用它交流 → 移到名称列副行或详情页 |

### H4　后端字段富余，前端利用率低

`_to_view()`（`platform/datasource/service.py:418-444`）返回 **20 个字段**：

```
id, code, name, ds_type, host, port, environment, group_name,
owner_business, owner_technical, enabled, scan_enabled, sampling_enabled,
supports_*, last_scan_at, last_scan_status, last_error, credential_versions, ...
```

前端 `DataSource` 类型只声明了 **7 个**（`id/code/name/dsType/enabled/createdAt/updatedAt`）。**列表页用了 5 个，详情页用了 6 个。**

### H5　操作列有三种状态

| 状态 | 页面 | 详情 |
|---|---|---|
| **完整** | 订阅（启停/删除）、任务（详情/取消/重试）、审批（详情/通过/驳回） | 符合规约，且危险操作都有 `ConfirmDanger` ✅ |
| **缺失** | **变更**（完全无操作列）、**术语**（完全无操作列） | 规约要求变更页有「操作(详情)」并支持确认动作——无处触发 |
| **不全** | **数据源**（扫描/分级/停用，缺编辑、缺详情） | `updateDataSource` API 前后端都已实现，**零页面调用**——改配置只能删除重建 |

## 二、逐页信息架构评估

**核心任务**：纳管了哪些库；分别是哪个环境、谁的；现在通不通；该不该动它。

| 判断要不要处理 | 健康 / 最近扫描结果 | ❌ 列表没有（详情页有） | 缺失 |
| 修改配置 | 编辑入口 | ❌ 操作列只有扫描/分级/停用 | **缺失** |
| — | — | ⚠️ `ID` 列 | **删除**（代理主键） |
| — | — | ⚠️ `编码` 列 | **降级**（内部编码，进副行） |

**列 diff（FE-01 §3.1 vs 实现）**

| 列 | 规约 | 实现 | 判定 |
|---|---|---|---|
| 名称 | ✅ | ✅（纯文本） | 保留，**改造为详情链接** |

| 分组 | ✅ | ❌ | 补（可后置或进筛选） |
| 负责人 | ✅ | ❌ | **补** |
| 扫描开关 | ✅ | ❌ | 补（可合并进「健康」或操作列） |
| 采样开关 | ✅ | ❌ | 补（同上） |

| — | ❌ | ✅ `ID` | **删** |

**结论**：删 1 列（ID）、降级 1 列（编码）、补 4–5 列（地址/环境/负责人/健康）、操作列补 1 个入口（编辑）。
改造后列结构见 §四。

**附带**：筛选栏只有 关键字/类型/状态，而后端 `list_datasources` 已支持 `environment` / `group_name` 参数——**白白浪费**。

## 四、数据源列表改造方案（双行主副形态）

**零后端改动。** `_to_view()` 已返回全部所需字段，`list_datasources` 已支持 `environment`/`group_name` 筛选参数。

### 目标列结构

```
名称 / 连接地址              | 类型 | 环境 | 负责人 | 健康      | 操作
─────────────────────────────────────────────────────────────────────────
pg_local                    | PG   | 生产 | 张伟   | ● 正常    | 扫描 分级 编辑 停用
10.0.1.23:5432              |      |      |        |           |
mysql_ods                   | MySQL| 测试 | 李娜   | ● 异常    | 扫描 分级 编辑 停用
10.0.1.45:3306              |      |      |        |           |

—                           |      |      |        |           |
```

### 列定义

| 列 | 数据源 | 渲染规则 |
|---|---|---|
| **名称 / 连接地址**（双行） | `name` + `host`/`port` | 主行 `name` 渲染为 `<Link to={/app/datasources/${id}}>`（**详情入口从 ID 列移到这里**）；副行 `host:port` 用 mono 小字灰；`host` 缺失时副行显示 `code`，都缺则显示 `—` |
| **类型** | `ds_type` | 走 G1 字典层显示中文（`postgresql`→`PostgreSQL`） |
| **环境** | `environment` | 直接显示；空值 `—`（已有数据可能为空，需能容忍） |
| **负责人** | `owner_business` | 优先业务负责人，缺失回退 `owner_technical`，都缺 `—` |
| **健康** | `last_scan_status` + `last_error` | 三态：正常（绿，扫描成功）/ 异常（红，`last_error` 进 Tooltip）/ 未扫描（灰，`last_scan_at` 为空）。**用列表已有字段推导，不额外发请求** |
| **操作** | — | `扫描` `分级` `编辑` `停用|启用`。编辑打开 `DataSourceForm` 抽屉（FE-01 §3.2）调 `updateDataSource`；停用保持 `ConfirmDanger` |

### 删除 / 降级

- **删**`ID` 列（代理主键，入口已移到名称列）
- **降级**`编码` 列 → 名称列副行（`host` 缺失时的回退值）
- `状态`（启用/停用 Tag）**并入健康列或保留为独立列**——需你定：健康与启用是两个维度（可能"已停用但上次扫描正常"），我倾向**保留独立的状态列**，共 6 列。

### 筛选栏补充

现有：关键字 / 类型 / 状态。**补**：环境（`environment`）、分组（`group_name`）——后端参数已就绪。

### 为什么是双行而不是加一列

`host:port` 单独占一列会再加 140px 宽，在已有 6 列的基础上必然触发横向滚动，把"操作"列挤出视野；而它和名称是同一件事的两面（**这个库是什么 / 它在哪**），合并语义自洽。参考 `TableDetailPage` 已有的 FQN 副行呈现方式，保持一致。

## 五、实施顺序与范围建议

### 整体变更（横切，建议先做）

| # | 变更 | 覆盖 | 是否需后端 |
|---|---|---|---|
| **G-A** | 删 6 页的裸 ID 列，详情入口挂到名称/标题/FQN | 数据源/变更/订阅/术语/审批/工单 | ❌ 纯前端 |
| **G-B** | 数据源列表补判断类字段（地址/环境/负责人/健康）+ 编辑入口 | 数据源 | ❌ 纯前端（字段已在返回里） |
| **G-C** | 变更列表补操作列与「数据源」列，FQN 加链接 | 变更 | ❌ 纯前端 |
| **G-D** | 筛选「数据源」从手输 ID 改下拉 | 变更/任务/资产目录 | ❌ 纯前端 |
| **G-E** | 补缺失的判断类列（进度/SLA/优先级/创建时间） | 任务/工单/审批 | ❌ 纯前端 |

### 局部变更（逐页，不动结构）

- 术语表补操作列（S2-7）+ **补 FE-01 §12.1 规约**
- 审计列表详情列改抽屉（S3-2，存量）
- 枚举走字典层（S3-4，即上一轮 G1，横切）

### 建议节奏

1. **先做 G-A + G-B（数据源一页做透）** —— 它是你点名的例子，且能一次性验证"删 ID / 补判断字段 / 双行副行 / 补编辑入口"这套模式是否好用；
2. 模式确认后再推 G-A 到其余 5 页（机械但量大）；
3. G-C/G-D/G-E 按模块排期，其中**变更列表无操作列（S1-2）建议优先级提到最前**——它是唯一一个"核心动作无入口"的页面。
