## 2. 严重设计风险

### R1 · DDL 与 ORM 双真相源（严重）

**问题**：`02-schema-ddl.sql` 是手写的完整 DDL（约 36 张表）。若实施时再写一套 SQLAlchemy ORM 模型，就存在两个真相源。模型演进时必然漂移——改了 ORM 忘了改 DDL，或反之。

**影响**：迁移与环境不一致；后期排查成本极高。

**修订**：**ORM 为唯一真相源**，Alembic autogenerate 生成迁移，`02-schema-ddl.sql` 降级为「设计参考快照」。已在 T-102 落地。

### R2 · 分区表与 Alembic 不匹配（严重）

**问题**：

- Alembic `autogenerate` 不会生成 `PARTITION BY` 子句，分区表必须手写迁移
- 按月分区需要**运行时预建**（每月建下月分区），这不是迁移能做的事
- 大表 `CREATE INDEX CONCURRENTLY` **不能在事务块内执行**，而 Alembic 默认把迁移包在事务里

**影响**：迁移执行失败，或上线后分区缺失导致写入报错。

**修订**：① 分区表迁移手写并显式 `PARTITION BY`；② 分区预建与 DROP 独立为运维定时任务（挂 T-107 编排）；③ CONCURRENTLY 索引用 `autocommit_block()` 或在迁移外执行。已在 T-102 / T-106 落地。

## 3. 任务遗漏（设计有要求，计划无任务）

### R9 · 元数据抽取 Dialect 抽象层漏排 ⚠ 阻塞 MOD-02

**依据**：MOD-02 §7.1-D1「建立 `Dialect` 抽象层，消除各连接器重复 SQL 与硬编码类型映射（现状 `postgres.py:329-393`）」，对应 FR-2.4。

**计划现状**：只有 T-301 排了**采样**方言（`Dialect.sample_sql`），**元数据抽取方言（系统表查询 + 类型归一化）完全没有任务**。

**影响**：不做这层，类型归一化散落在三个连接器里，`PostgresSink` 落库时拿到的 `data_type` 口径不统一，`struct_hash` 也会因类型串差异产生假变更（同一结构在不同库被算出不同签名）→ **直接污染版本 Diff 的正确性**。

**修订**：增补 **T-114 元数据抽取 Dialect 抽象**，且必须早于 T-105 落库。

### R10 · `DatabasePipeline` 缺 transform 钩子漏排

**依据**：MOD-02 §7.1 缺陷 2 —— `database_pipeline.py:261,391,405` 直接 `sink.write_table`，绕过 `TablePipeline.transform`（`:211,257`）。

**影响**：两条流水线行为不一致。后续任何处理逻辑（含分类分级钩子）会被 DatabasePipeline **静默绕过**，表现为「部分表有标签、部分没有」的诡异 bug，排查极难。

**修订**：增补 **T-115 补齐 DatabasePipeline transform 钩子**，归入 B0。

### R11 · API 序列化层（camelCase ⇄ snake_case）漏排

**依据**：`03-openmetadata-compatibility.md` §4 —— DB 层 snake_case，API/交换层 camelCase（对齐 OpenMetadata）。

**计划现状**：无任何任务负责这层映射。

**影响**：要么 API 直接暴露 snake_case（丧失 OpenMetadata 兼容，违反 ADR-8），要么每个模块各写各的转换（不一致且重复）。

**修订**：增补 **T-112 API 序列化层**，归入 B0，早于所有 API 任务（T-109、B1b）。

### R12 · 性能验证造数脚本漏排

**依据**：计划 §7 要求性能用例覆盖「分页 P95 < 500ms、批量写入分钟级」，但**没有任务产出验证数据**。用户明确不做 PoC，但常规性能用例仍需数据支撑。

**修订**：增补 **T-113 造数脚本**（可配置规模，默认 30 万表 / 1000 万字段），归入 B0，供各批次复用。
